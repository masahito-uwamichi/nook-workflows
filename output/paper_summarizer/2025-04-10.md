
# Leanabell-Prover: Posttraining Scaling in Formal Reasoning

[View Paper](http://arxiv.org/abs/2504.06122v2)

## 1. 既存研究では何ができなかったのか

既存研究におけるLLMを用いた自動定理証明(ATP)は、Open AI O1/O3やDeepseek R1などの自然言語処理における大規模モデルのポストトレーニングによる劇的な性能向上を十分に活用できていませんでした。具体的には以下の点が課題でした。

*   **自然言語とのギャップ:** 自然言語による数学の問題解決では高い性能を示すLLMも、Lean 4のような形式言語で証明を生成するのは難しい。形式言語で記述されたデータが不足しているため、自然言語と形式言語の間のギャップを埋められませんでした。
*   **中間フィードバックの欠如:** Whole-proof生成アプローチは、LLMの自然言語推論と高度な計画能力を活用できますが、形式言語エグゼキュータからの即時的なフィードバックがありません。そのため、生成された証明はエラーの事後分析が不足し、自明でない解決策を必要とする問題では性能が低下します。
*   **認知的な行動の欠如:** 人間のような推論能力（検証、バックトラッキング、サブゴールの設定、後方推論など）を統合しないと、強化学習(RL)アルゴリズムを適用しても大幅な改善は難しいことが指摘されていました。
*   **RLの潜在能力の未活用:** 自然言語処理でのRLの成功に比べ、形式言語推論における改善の余地は大きいにもかかわらず、既存のRLトレーニングアプローチをそのまま適用することは困難でした。DeepSeek-Prover-v1.5-RLでも、教師ありファインチューニング(SFT)モデルからの改善はわずか1.8%でした。

## 2. どのようなアプローチでそれを解決しようとしたか

本研究では、ATPモデルのポストトレーニング全体を調査し、自然言語における推論モデルのブレークスルーに近づけることを目指しました。具体的には以下の3つの段階でアプローチしました。

1.  **ハイブリッドデータセットによる継続的なトレーニング (Continual Training):**
    *   既存のATPモデルを、ステートメントと証明のペア、および人間のような推論と仮説の洗練をエミュレートする認知的な行動を組み込むことを目的とした追加データからなるハイブリッドデータセットで継続的にトレーニングしました。
    *   合成データを使用してモデルに自己反省能力を埋め込みました。具体的には、Leanの補完（Lean completion）と書き換え（rewriting）という2種類のChain of Thought(CoT)テンプレートを使用しました。
        *   Lean completionでは、不完全な証明を修正し、Claudeのような大規模言語モデルを用いて、誤った箇所と正しい解決策を比較した反省的な応答を生成させました。
        *   書き換えでは、まずQwen2.5-72B-instructを用いて問題解決のコメントを評価し、必要に応じて修正します。その後、Claudeに無効なコードと修正されたコードの両方を提供し、推論プロセスを説明するCoTを生成させました。

2.  **Lean 4コンパイラによる報酬を用いた強化学習 (Reinforcement Learning):**
    *   Lean 4コンパイラから返される結果報酬を用いて強化学習を探求しました。コンパイルが成功した場合は正の報酬、構文エラーやタイムアウトの場合は負の報酬を与えました。
    *   GRPO (Generative Pre-trained Transformer Reward Proxy Optimization)アルゴリズムを使用し、グループレベルの報酬を正規化してアドバンテージを計算しました。

3.  **Leanabelle-Proverの構築:**
    *   上記の継続的なトレーニングと強化学習プロセスを通じて、DeepSeek-Prover-v1.5 と Goedel-Proverを含む既存の形式証明器を改善し、whole-proof生成の分野で最先端のパフォーマンスを達成しました。
    *   2つのベースモデル(DeepSeek-Prover-v1.5-SFTとGoedel-Prover-SFT)からポストトレーニングされたLeanabell-Prover-DSとLeanabell-Prover-GDを構築しました。

## 3. 結果、何が達成できたのか

本研究により、以下の成果が得られました。

*   **MiniF2Fでの性能向上:** MiniF2Fベンチマークにおいて、59.8% (pass@32) の合格率を達成しました。
*   **既存モデルの改善:** 既存の形式証明器であるDeepSeek-Prover-v1.5とGoedel-Proverを改善しました。例えば、Goedel-Prover-RLは、DeepSeek-Prover-v1.5-RLを6.6%、Goedel-Prover-SFTを2.2%上回りました。
*   **自己反省能力の導入:** 合成データを用いて、モデルに自己反省のような認知的な行動を導入しました。
*   **データセットの公開:** 152万件の形式ステートメントと、22万件の詳細な非形式的なCoTと検証済み証明を含むデータセットを公開しました。([https://github.com/Leanabell-LM/Leanabell-Prover](https://github.com/Leanabell-LM/Leanabell-Prover))
*   **最先端性能:** 提案手法 Leanabelle-Prover は、MiniF2F-test で 59.8% (pass@32) を達成し、最先端の性能を示しました。

## 4. Limitationや問題点は何か

論文で言及されている制限事項と、それ以外に考えられる制限事項を以下に示します。

*   **自己反省能力の弱体化:** RLトレーニング後、統合された自己反省能力が弱まる傾向が見られました。弱い基盤LLMに認知的な行動を効果的に統合することは依然として難しいことを示唆しています。
*   **計算リソース:** 大規模なデータセットを扱うため、トレーニングには相当な計算リソースが必要です。
*   **RLの潜在能力の制約:** 自然言語処理に比べると形式言語におけるRLの潜在能力を最大限に引き出せていない可能性があります。RLのプロンプトセットの選択は重要ですが、pass@Nのみを基準とするだけでは不十分です。
*   **汎用性の課題:** MiniF2Fでの性能は向上しましたが、他の形式言語や、より複雑な定理証明問題への適用可能性は不明です。データセットの偏りが存在する可能性があり、特定の数学分野に特化したデータ拡張が必要となる場合があります。
*   **ベースモデルの能力:** DeepSeek-Prover-v1.5は、Deepseek v3やQwen2.5ファミリーのような自然言語処理におけるポストトレーニングスケーリングに使用されるLLMに比べて弱いLLMです。そのため、期待されるほど強力なRL性能が実現しませんでした。
*   **報酬設計の限界:** Lean4コンパイラの検証結果を報酬として使用していますが、より詳細な中間ステップでのフィードバックを活用することで、より効率的な学習が可能になる可能性があります。

## 5. 技術的な詳細について

以下に技術的な詳細をまとめます。

*   **モデル:** DeepSeek-Prover-v1.5-SFT と Goedel-Prover-SFT (70億パラメータ) をベースモデルとして使用。これらのモデルは、詳細な解説コメント付きの証明でトレーニングされており、自然言語記述とLean 4コードを対応させる基本的な能力を持っています。
*   **データセット:**
    *   **初期トレーニングデータ:** Mathlib4のような既存のLean 4の数学ライブラリや、NuminaMath、AoPSなどの多様なソースから収集した152万件の形式ステートメントと、22万件の詳細な非形式的なCoTと検証済み証明のデータセットを使用。
    *   **合成データ:** Qwen2.5-32B-Coder-InstructをベースとしたFormalizerを用いて自然言語の数式問題をLean 4の形式ステートメントに変換。PromptCoTフレームワークを用いて、AMC、AIME、USAMOなど様々なレベルの数学問題を生成。
*   **トレーニング:**
    *   **SFT (Supervised Fine-Tuning):** 8 NVIDIA H100 GPUを使用。学習率は5e-5、グローバルバッチサイズは32、エポック数は2、Weight Decayは0.1。
    *   **継続的なトレーニング (Continual Training):** 学習率は5e-5、グローバルバッチサイズは1024、エポック数は1。
    *   **RL (Reinforcement Learning):** 学習率は1e-6。各定理に対して32個の候補証明をサンプリングし、最大ロールアウト長は8192。グローバルバッチサイズは16。Pass@32が[2,16]の範囲にあるサンプルを選択。GRPOを使用。
*   **報酬関数:**
    ```python
    def reward_function(compilation_result):
      if compilation_result == "success":
        return R_success  # 例: 1.0
      else: # compilation_result == "failure":
        return R_fail     # 例: -1.0
    ```

*   **Formalizer:** Qwen2.5-32B-Coder-Instructをベースに、学習率は5e-6でトレーニング。

# SkillWeaver: Web Agents can Self-Improve by Discovering and Honing Skills

[View Paper](http://arxiv.org/abs/2504.07079v1)

## 1. 既存研究では何ができなかったのか

既存の自律的なウェブエージェントは、複雑な環境で生き残り、成長するために必要な、洗練された自己改善メカニズムを十分に備えていません。具体的には、以下の点が課題として挙げられます。

*   **手続き型知識の抽象化の困難性:** ウェブサイトの操作手順を再利用可能な形（スキル）として抽象化することが難しい。
*   **スキルの洗練の困難性:** 一度獲得したスキルを、経験を通じて改善・最適化することが難しい。
*   **スキル合成の困難性:** 複数のスキルを組み合わせて、より複雑なタスクを達成することが難しい。

これらの課題により、既存のウェブエージェントは、環境の変化に適応し、継続的に能力を向上させることが困難でした。

## 2. どのようなアプローチでそれを解決しようとしたか

本研究では、SkillWeaverというスキル中心のフレームワークを提案することで、上記の問題を解決しようとしました。SkillWeaverの主なアプローチは以下の通りです。

1.  **スキルの自律的な発見:** 新しいウェブサイトにアクセスした際に、エージェントが自動的に実行可能な操作（スキル）を特定します。
2.  **スキルの実行と練習:** 発見したスキルを実際に実行し、その経験を通じてスキルの理解を深めます。
3.  **APIとしてのスキルの抽出:** スキルの実行経験を元に、その操作を軽量で再利用可能なAPIとして抽出します。これにより、手続き型知識の抽象化を実現します。
4.  **スキルの反復的な探索:** 反復的な探索を通じて、APIライブラリを継続的に拡張します。
5.  **スキル共有:** 複数のエージェント間でAPI（スキル）を共有することで、知識の伝達を可能にします。

## 3. 結果、何が達成できたのか

SkillWeaverを導入した結果、以下の点が達成されました。

*   **WebArenaにおける性能向上:** WebArena環境での相対成功率が31.8%向上しました。
*   **実世界のウェブサイトにおける性能向上:** 実世界のウェブサイトでの相対成功率が39.8%向上しました。
*   **スキル転送による性能向上:** 強力なエージェントが生成したAPIを弱いエージェントに転送することで、WebArenaにおいて最大54.3%の性能向上が見られました。

これらの結果から、SkillWeaverが、様々なウェブエージェント間でシームレスに共有可能なAPIとして、ウェブサイトの相互作用を洗練するのに効果的であることが示されました。

## 4. Limitationや問題点は何か。本文で言及されているものの他、あなたが考えるものも含めて

本文からは具体的なLimitationsや問題点は読み取れません。私が考える問題点と合わせて以下に示します。

*   **探索の効率性:** エージェントがスキルを探索する際、効率的な探索戦略が必要となります。闇雲に探索するだけでは、時間や計算資源を浪費する可能性があります。
*   **スキルの複雑性:** 単純なスキルだけでなく、複雑なスキルをどのように発見し、抽象化するかが課題となります。
*   **APIの汎用性:** 特定のウェブサイトに特化したAPIではなく、より汎用的なAPIを生成する必要があります。
*   **安全性:** 悪意のあるウェブサイトにアクセスした場合、生成されたAPIが悪用される可能性があります。安全性を考慮したAPI設計が求められます。
*   **評価の難しさ:** スキルの有効性を客観的に評価することが難しい場合があります。特に、複雑なタスクを達成するためのスキルについては、適切な評価指標を設計する必要があります。
*   **環境依存:** ウェブサイトの構造やデザインが変更された場合、既存のAPIが動作しなくなる可能性があります。環境変化へのロバスト性を高める必要があります。

## 5. 技術的な詳細について。技術者が読むことを想定したトーンで

SkillWeaverの中核は、WebサイトのインタラクションをAPIとして抽象化するプロセスです。

1.  **スキル発見:** まず、エージェントはWebページのDOM構造を解析し、`<a>`, `<button>`, `<input>`などのインタラクティブな要素を特定します。これらの要素に対するクリックや入力操作が、潜在的なスキル候補となります。

2.  **スキル実行と記録:** スキル候補に対して、実際に操作を実行し、その結果を記録します。この際、操作前のDOM構造、操作内容、操作後のDOM構造などを記録し、スキルの入出力関係を学習するためのデータセットを構築します。

3.  **API生成:** 記録されたデータセットを元に、スキルをAPIとして実装します。APIは通常、以下の要素を含みます。
    *   **入力:** スキル実行に必要なパラメータ（例：テキストボックスへの入力値）。
    *   **実行関数:** 実際にWebサイトを操作する関数（例：指定された要素をクリックする）。
    *   **出力:** スキル実行後の状態（例：DOM構造の変化、特定の要素の値）。

4.  **スキル管理:** 生成されたAPIは、スキルライブラリに格納され、管理されます。APIは、その機能や実行条件に基づいて分類され、検索可能となります。

# Generative Evaluation of Complex Reasoning in Large Language Models

[View Paper](http://arxiv.org/abs/2504.02810v1)

## 1. 既存研究では何ができなかったのか

既存のLLM評価ベンチマークは、公開後にLLMの学習データに組み込まれることで汚染され、モデルが単に記憶した知識を再現しているのか、真に推論しているのかを区別できなくなるという問題がありました。つまり、LLMの推論能力を忠実に評価することが困難でした。

## 2. どのようなアプローチでそれを解決しようとしたか

KUMOという生成評価フレームワークを導入することで、この問題を解決しようとしました。KUMOは、LLMと記号エンジンを組み合わせ、多様で多段階の推論タスクを動的に生成します。これらのタスクは部分的にしか観測できず、難易度を調整可能です。自動化されたパイプラインを通して、KUMOはオープンエンドなドメインにわたって新しいタスクを継続的に生成し、モデルが単なる記憶ではなく、真の汎化能力を示すように促します。

## 3. 結果、何が達成できたのか

KUMOを用いて23個の最先端LLMを、100個のドメインにわたる5,000個のタスクで評価しました。LLMの推論能力を大学生と比較した結果、多くのLLMが簡単な推論タスクで大学生レベルのパフォーマンスを上回り、推論スケールされたLLMが複雑な推論課題で大学生レベルのパフォーマンスに達することがわかりました。さらに、KUMOタスクにおけるLLMのパフォーマンスは、新たに公開された現実世界の推論ベンチマークの結果と強く相関しており、KUMOがLLMの真の推論能力を評価するための堅牢で永続的なツールとしての価値を持つことを示唆しています。

## 4. Limitationや問題点は何か

*   **生成されるタスクの妥当性:** KUMOによって生成されるタスクの品質がLLMの評価に大きく影響します。タスクが現実世界の推論をどの程度反映しているか、タスクの難易度設定の適切さなどが課題となります。
*   **評価指標の限界:** 現在の評価指標がLLMの推論能力を完全に捉えているとは限りません。より高度な推論能力を評価できるような新しい指標が必要になる可能性があります。
*   **計算コスト:** KUMOはタスクの生成とモデルの評価に計算資源を必要とします。特に複雑なタスクや大規模なモデルを評価する場合、コストが大きくなる可能性があります。
*   **ドメイン知識の偏り:** KUMOが生成するタスクは、使用するLLMや記号エンジンのドメイン知識に依存する可能性があります。偏りのない評価を行うためには、多様な知識源を活用する必要があります。
*   **大学生との比較:** 大学生との比較は一つの目安にはなりますが、LLMの推論能力の絶対的な評価基準とは言えません。より専門的な知識や高度な推論能力を要求するタスクでの評価も必要でしょう。

    ```python
    def evaluate_model(model, task, ground_truth):
    ```

# ProtoGCD: Unified and Unbiased Prototype Learning for Generalized Category Discovery

[View Paper](http://arxiv.org/abs/2504.03755v1)

## 1. 既存研究では何ができなかったのか

Generalized Category Discovery (GCD)タスクにおいて、既存研究は以下の点で課題を抱えていました。

*   **クラス間の精度不均衡:** Pseudo-labelingを用いたparametric classifierを使用する初期の研究では、oldクラスとnewクラスを別々に扱い、学習目標も分けていたため、oldクラスへのバイアスが生じ、クラス間で精度に不均衡が生じていました。
*   **偏った表現:** Contrastive learningを用いる最近の手法では、潜在的な正例を無視したり、クラスタリングの目的から乖離していたため、偏った表現が学習され、結果が最適とは言えませんでした。
*   **実用性の欠如:** ほとんどの手法では、newクラスの数を事前に知っていることを前提としていましたが、これは現実的ではありませんでした。
*   **タスクレベルの非統一性:** oldクラスの分類とnewクラスのクラスタリングに留まり、異常検知などのタスクへの拡張がされていませんでした。

## 2. どのようなアプローチでそれを解決しようとしたか

これらの課題を解決するために、ProtoGCD (Unified and Unbiased Prototype Learning framework) を提案しました。主なアプローチは以下の通りです。

*   **統一的なモデリング:** oldクラスとnewクラスをjointなプロトタイプでモデル化し、統一的な学習目標を用いることで、クラス間の精度不均衡を緩和しました。 具体的には、全てのクラス(old/new)に対して、共有のfeature spaceと、同じlearnable prototypesを使用します。
*   **バイアス軽減のためのメカニズム:**
    *   Dual-Level Adaptive Pseudo-Labeling (DAPL) メカニズムを導入し、confirmation biasを軽減しました。 DAPLでは、サンプルに対するpseudo-labelのタイプ(hard/soft)と割合を、サンプルのconfidenceとモデルのperformanceに応じて適応的に調整します。
    *   クラスタリングの自明な解を避けるために、marginal entropy maximizationとinter-class separation regularizationという2つの正則化項を追加し、表現の改善を図りました。
*   **クラス数推定:** 特徴空間とoldクラスの分類性能を同時に考慮する新しい基準を考案し、newクラスの数を推定できるようにしました。 具体的には、ラベル付きデータの精度と、ラベル付きデータとラベルなしデータの重心の乖離度を組み合わせてスコアを計算し、最適なクラス数を探索します。
*   **タスクレベルの統一:** ProtoGCDを拡張し、unseen outlierの検出を可能にすることで、タスクレベルでの統一性を実現しました。

## 3. 結果、何が達成できたのか

ProtoGCDによって、以下の成果を達成しました。

*   **最先端の性能:** genericなデータセットとfine-grainedなデータセットの両方で、既存のstate-of-the-artな手法を大幅に上回る性能を達成しました。
*   **精度の均衡:** oldクラスとnewクラス間の精度バランスが改善されました。
*   **クラス数推定の高精度化:** 従来手法よりも正確なクラス数推定を実現しました。
*   **タスクの統一:** outlier検出への拡張により、タスクレベルでの統一性を達成しました。
*   **ロバスト性:** 様々なデータセットや設定で高い性能を達成し、ロバスト性を示しました。

## 4. Limitationや問題点は何か。本文で言及されているものの他、あなたが考えるものも含めて

論文で言及されている制限事項：

*   **長尾分布への対応:** Herbデータセットのような長尾分布データセットにおいて、 marginal entropy maximizationは、データセットの分布と矛盾する可能性があり、性能に影響を与える可能性があります。ただし、論文内では、この点について詳細な分析が行われており、適切な重み調整によって性能低下を抑制できることが示されています。
*   **信頼性キャリブレーション:** oldクラスとnewクラスの間の信頼性キャリブレーションが十分でないことが言及されています。

その他、私が考える制限事項：

*   **ハイパーパラメータ調整:** ProtoGCDは、DAPLの閾値や正則化項の重みなど、複数のハイパーパラメータを持ちます。これらのパラメータは、データセットやタスクによって最適な値が異なる可能性があり、調整に手間がかかる場合があります。
*   **計算コスト:** contrastive learningやpseudo-labelingを行うため、計算コストが高くなる可能性があります。特に大規模なデータセットや複雑なモデルを使用する場合は、GPUリソースや学習時間の制約を受ける可能性があります。
*   **理論的保証:** ProtoGCDは経験的に優れた性能を示していますが、その性能を保証する理論的な根拠はまだ確立されていません。
*   **データセットのバイアス:** 学習に使用するデータセットにバイアスが含まれている場合、ProtoGCDの性能が低下する可能性があります。例えば、特定のクラスのサンプル数が少ない場合や、特定の属性を持つサンプルが偏っている場合などです。
*   **ドメイン適応:** 学習に使用するデータセットとテストデータセットのドメインが異なる場合、ProtoGCDの性能が低下する可能性があります。例えば、異なるカメラで撮影された画像や、異なる照明条件で撮影された画像などです。

## 5. 技術的な詳細について。技術者が読むことを想定したトーンで

ProtoGCDの中核は、以下の要素で構成されています。

1.  **特徴抽出器:** 入力画像 $\mathbf{x}_i$ を受け取り、特徴表現 $\mathbf{z}_i = \mathcal{E}(\mathbf{x}_i)$ を生成します。 本論文では、ViT-B/16を特徴抽出器として使用し、最終Transformer blockの出力を利用しています。

2.  **プロトタイプ:** $K$ 個のlearnable prototype $\mathcal{P} = \{\bm{\mu}_c\}_{c=1}^{K}$ を保持します。ここで、$K = K_{old} + K_{new}$ は、oldクラスとnewクラスの総数です。 各プロトタイプ $\bm{\mu}_c$ は、$\ell_2$ 正規化された特徴空間に存在します。 特徴表現 $\mathbf{z}_i$ とプロトタイプ $\bm{\mu}_c$ のコサイン類似度に基づいて、サンプルが各クラスに属する確率を計算します（von Mises-Fisher (vMF) 分布を仮定）。
    ```python
    def cosine_similarity(z, mu):
        return np.dot(z, mu) / (np.linalg.norm(z) * np.linalg.norm(mu))

    def vmf_probability(z, mu, tau):
        # C_p は正規化定数（計算省略）
        C_p = ...
        return C_p * np.exp(cosine_similarity(z, mu) / tau)

    def posterior_probability(z, prototypes, tau):
        probabilities = [vmf_probability(z, mu, tau) for mu in prototypes]
        total_probability = sum(probabilities)
        return [p / total_probability for p in probabilities]
    ```

3.  **損失関数:**
    *   **Contrastive Loss ($\mathcal{L}_{con}$):**  Supervised Contrastive Learning (ラベル付きデータ) と Self-Supervised Contrastive Learning (ラベルなしデータ) を組み合わせることで、特徴表現の質を高めます。
        ```python
        def supervised_contrastive_loss(features, labels, tau_c):
            loss = 0
            for i in range(len(features)):
                positive_indices = [j for j in range(len(features)) if labels[i] == labels[j] and i != j]
                if len(positive_indices) == 0:
                    continue
                positive_loss = 0
                for q in positive_indices:
                    positive_loss += -np.log(np.exp(cosine_similarity(features[i], features[q]) / tau_c) /
                                            sum([np.exp(cosine_similarity(features[i], features[j]) / tau_c) for j in range(len(features)) if j != i]))
                loss += positive_loss / len(positive_indices)
            return loss / len(features)

        def unsupervised_contrastive_loss(features, tau_c):
            loss = 0
            for i in range(len(features)):
                loss += -np.log(np.exp(cosine_similarity(features[i], features[i_prime]) / tau_c) / # i_primeはiのaugmentされたview
                                sum([np.exp(cosine_similarity(features[i], features[j]) / tau_c) for j in range(len(features)) if j != i]))
            return loss / len(features)
        ```
    *   **Dual-Level Adaptive Pseudo-Labeling Loss ($\mathcal{L}_{dapl}$):**  サンプルの信頼度に応じて、Hard Pseudo-LabelとSoft Pseudo-Labelを適応的に割り当てることで、confirmation biasを軽減し、効率的なself-trainingを実現します。
        ```python
        def proto_confidence(z, prototype_1, prototype_2, tau):
            return np.exp(cosine_similarity(z, prototype_1) / tau) / np.exp(cosine_similarity(z, prototype_2) / tau)

        def adaptive_pseudo_label(z, prototypes, tau_base, tau_sharp, delta):
            probabilities = posterior_probability(z, prototypes, tau_base)
            top_1_index = np.argmax(probabilities)
            # 2番目に類似度の高いPrototype
            top_2_index = np.argsort(probabilities)[-2]

            if proto_confidence(z, prototypes[top_1_index], prototypes[top_2_index], tau_base) >= delta:
                # Hard Pseudo-Label
                q = np.zeros_like(probabilities)
                q[top_1_index] = 1.0
                return q
            else:
                # Soft Pseudo-Label (Sharpened)
                return posterior_probability(z, prototypes, tau_sharp)
        ```
    *   **Regularization Loss ($\mathcal{L}_{reg}$):** marginal entropy maximizationとinter-class separation regularizationの組み合わせにより、クラスタリングの自明な解を回避し、クラス間の分離を促進します。
        ```python
        def entropy(p):
            return -np.sum(p * np.log(p))

        def marginal_entropy_maximization(probabilities):
            marginal_probability = np.mean(probabilities, axis=0)
            return entropy(marginal_probability)

        def inter_class_separation(prototypes, tau_sep):
            loss = 0
            for i in range(len(prototypes)):
                other_prototypes_similarity = 0
                for j in range(len(prototypes)):
                    if i != j:
                        other_prototypes_similarity += np.exp(cosine_similarity(prototypes[i], prototypes[j]) / tau_sep)
                loss += np.log(other_prototypes_similarity / (len(prototypes) - 1))
            return loss / len(prototypes)
        ```
    *   **Supervised Loss ($\mathcal{L}_{sup}$):**  ラベル付きデータに対するcross-entropy lossです。

4.  **クラス数推定:** ラベル付きデータの分類精度 (accScore) と、ラベル付きデータとラベルなしデータの重心の乖離度 (centrScore) を組み合わせて、最適なクラス数を推定します。
    ```python
    def acc_score(model, labeled_data, labels):
        correct = 0
        for i in range(len(labeled_data)):
            z = model.encode(labeled_data[i]) # model.encode は特徴zを返す
            probabilities = posterior_probability(z, model.prototypes, model.tau_base)
            predicted_class = np.argmax(probabilities)
            if predicted_class == labels[i]:
                correct += 1
        return correct / len(labeled_data)

    def centr_score(prototypes_l, prototypes_u):
        score = 1.0
        for k in range(len(prototypes_l)):
            score *= cosine_similarity(prototypes_l[k], prototypes_u[k])
        return score
    ```

# V-MAGE: A Game Evaluation Framework for Assessing Visual-Centric Capabilities in Multimodal Large Language Models

[View Paper](http://arxiv.org/abs/2504.06148v1)

## 1. 既存研究では何ができなかったのか

既存の Multimodal Large Language Models (MLLMs) の評価ベンチマークは、主に以下の点で不十分でした。

*   **視覚中心的なタスクの欠如:** 既存のゲームベースのベンチマークは、テキストベースのゲームに依存しており、空間的、時間的、動的な複雑さを評価するのに必要な視覚的推論を十分に評価できませんでした。テキストで完全に表現可能なゲーム環境では、モデルは視覚情報をテキストに変換して推論を行うことができ、真の視覚的推論能力を測れていませんでした。
*   **現実世界の意思決定に必要な多様な推論スキルの評価不足:** 静的なデータセットからオープンワールドで動的な環境へと評価が移行する中で、既存のベンチマークは、長期計画や熟考といった高レベルの推論スキルを評価できていませんでした。
*   **エージェント戦略とモデルの区別:** 既存のベンチマークでは、モデル自体の能力とエージェントの戦略が混同されがちでした。これにより、モデルの視覚認識の限界や改善の方向性を特定することが困難でした。
*   **継続的な評価と改善:** 既存のベンチマークは、モデルの改善に合わせて難易度を調整することが難しく、モデルの能力向上の妨げとなっていました。

## 2. どのようなアプローチでそれを解決しようとしたか

V-MAGE は、これらの問題を解決するために、以下の特徴を持つゲームベースの評価フレームワークを導入しました。

*   **視覚入力のみに基づく評価:** モデルはゲームのピクセルレベルのスクリーンショットのみを入力として受け取り、視覚的なシーン理解、オブジェクト追跡、空間的・時間的推論を必要とします。
*   **連続空間環境の導入:** グリッドベースのベンチマークとは異なり、連続空間環境を提供することで、モデルは無限に近い状態空間を探求し、単一の正解が存在しない状況で評価されます。
*   **難易度別のレベルデザイン:** 各ゲームは異なる難易度レベルで設計されており、モデルの様々なスキル（障害物、加速、一人称視点 vs. マップビューなど）を個別に評価できます。
*   **エージェントスキル評価の導入:** モデル評価に加えて、エージェントの戦略も評価できるパイプラインを構築しました。これにより、MLLM とエージェント戦略の両方を最適化できます。具体的には、Gameモジュール、Agentモジュール、Modelモジュールという3つのモジュールから構成される評価パイプラインを構築し、エージェント戦略とモデルを分離して評価できるようにしました。
*   **動的な Elo レーティングシステム:** モデルのパフォーマンス比較に動的な Elo システムを使用することで、手動によるスコアの正規化やパフォーマンスの上限を回避し、モデルの改善に合わせた評価を可能にしました。

## 4. Limitationや問題点は何か

V-MAGE の Limitation と問題点として、以下のような点が挙げられます。

*   **ゲーム環境の限定性:** V-MAGE は 5 種類のゲームを使用していますが、現実世界の視覚的な複雑さを完全に網羅しているわけではありません。より多様なゲームやタスクを追加することで、評価の信頼性を向上させる必要があります。

*   **評価のバイアス:** V-MAGE はビデオゲーム環境を完全に表現しているわけではないため、モデルの能力評価に偏りが生じる可能性があります。

V-MAGE の技術的な詳細は以下の通りです。

    *   **Agent モジュール:** 視覚入力を処理し、過去のフレーム、推論履歴、テキストプロンプト（ゲームルールなど）を統合して、MLLM への入力を構築します。

```python
def calculate_expected_score(rating_a, rating_b):

    return 1 / (1 + 10**((rating_b - rating_a) / 400))

def update_rating(rating, expected_score, actual_score, k=32):

    return rating + k * (actual_score - expected_score)
```

# HybriMoE: Hybrid CPU-GPU Scheduling and Cache Management for Efficient MoE Inference

[View Paper](http://arxiv.org/abs/2504.05897v1)

## 1. 既存研究では何ができなかったのか

既存研究におけるハイブリッドCPU-GPU推論は、MoEモデルのexpert activation patternsが非常に不安定であるため、固定されたマッピング戦略が非効率になるという問題がありました。また、expertのサイズや構造の多様性、ワークロードの偏りなどにより、ハイブリッドCPU-GPUスケジュールの複雑さも課題でした。具体的には、expert offloadingによるオーバーヘッドが大きく、リソース効率の向上が困難でした。

## 2. どのようなアプローチでそれを解決しようとしたか

HybriMoEは、以下の3つのアプローチで上記課題を解決しようとしました。

1.  **Dynamic Intra-Layer Scheduling:** CPUとGPU間でのワークロードを動的にバランスさせることで、リソース使用率を最適化します。
2.  **Impact-Driven Inter-Layer Prefetching:** expertの活性化パターンに基づいて、次のレイヤーで必要となるexpertを事前にCPUからGPUへロードすることで、expert offloadingのオーバーヘッドを軽減します。prefetchの優先度は、各expertが推論結果に与える影響度に基づいて決定されます。
3.  **Score-Based Caching Algorithm:** expert activationの不安定さを緩和するために、expertの活性化頻度や重要度に基づいてキャッシュを行い、よく使用されるexpertをGPU上に保持します。

## 3. 結果、何が達成できたのか

HybriMoEは、既存の最先端ハイブリッドMoE推論フレームワークと比較して、prefillステージで平均1.33倍、decodeステージで平均1.70倍の高速化を達成しました。これは、動的なスケジューリング、prefetching、キャッシュの組み合わせにより、リソース利用率が向上し、expert offloadingのオーバーヘッドが削減された結果です。

## 4. Limitationや問題点は何か

*   **本文で言及されているもの:**
    *   MoEモデルのexpert activation patternsが不安定なため、キャッシュ戦略が常に最適とは限らない可能性があります。
    *   ハイブリッドCPU-GPUスケジュールは本質的に複雑であり、完全に最適化することは困難です。
*   **私が考えるもの:**
    *   prefetchingの精度が重要であり、誤ったexpertをprefetchingすると、逆にオーバーヘッドが増加する可能性があります。
    *   フレームワークの複雑さが増し、デバッグやメンテナンスが難しくなる可能性があります。
    *   HybriMoEの効果は、MoEモデルの特性（expert数、サイズ、活性化パターンなど）に大きく依存する可能性があり、特定のモデルに特化している可能性があります。
    *   実験環境の詳細（CPU/GPUの種類、メモリサイズなど）が不明であり、異なる環境での性能が保証されるわけではありません。

## 5. 技術的な詳細について

HybriMoEは、CPUとGPU間でのデータ転送を最小限に抑えつつ、各expertの計算を効率的に実行するために、以下の技術を使用しています。

1.  **Dynamic Intra-Layer Scheduling:**
    ```python
    def schedule_layer(experts, input_data, cpu, gpu):
        # 各expertのワークロードを見積もる（例：入力サイズ、モデルサイズに基づく）
        workloads = estimate_workloads(experts, input_data)

        # CPUとGPUの処理能力を考慮して、expertを割り当てる
        cpu_load = cpu.get_current_load()
        gpu_load = gpu.get_current_load()

        for expert, workload in zip(experts, workloads):
            if cpu_load < gpu_load:
                cpu.execute(expert, input_data)
                cpu_load += workload
            else:
                gpu.execute(expert, input_data)
                gpu_load += workload
    ```

2.  **Impact-Driven Inter-Layer Prefetching:**
    ```python
    def prefetch_experts(current_layer_output, next_layer_experts, cache):
        # 各expertが次のレイヤーの出力に与える影響を予測する
        impact_scores = predict_impact(current_layer_output, next_layer_experts)

        # 影響度の高いexpertから順にprefetchする
        for expert, score in sorted(zip(next_layer_experts, impact_scores), key=lambda x: x[1], reverse=True):
            if not cache.contains(expert):
                load_expert_to_gpu(expert)
                cache.add(expert)
    ```

3.  **Score-Based Caching Algorithm:**
    ```python
    class ExpertCache:
        def __init__(self, capacity):
            self.capacity = capacity
            self.cache = {}
            self.scores = {}

        def add(self, expert):
            if len(self.cache) >= self.capacity:
                # スコアの低いexpertを削除する
                min_score_expert = min(self.scores, key=self.scores.get)
                del self.cache[min_score_expert]
                del self.scores[min_score_expert]

            self.cache[expert] = expert_data
            self.scores[expert] = 0  # 初期スコア

        def get(self, expert):
            if expert in self.cache:
                self.scores[expert] += 1 # アクセス時にスコアを更新
                return self.cache[expert]
            else:
                return None
    ```

# Efficient Reinforcement Finetuning via Adaptive Curriculum Learning

## 1. 既存研究では何ができなかったのか

*   **サンプル効率と計算効率の悪さ:** 大量のトレーニングデータと計算リソースを必要とし、スケーリングが困難でした。
*   **アルゴリズムの単純化によるトレードオフ:** RAFTなどのアルゴリズム簡略化手法は、効率は向上するものの、分散の増加や安定性の低下を招く可能性がありました。
*   **データ中心戦略の脆弱性:** LIMOなどのデータ中心戦略は、静的なデータフィルタリングやスコアリングに依存しており、モデル固有の問題が生じる可能性や、計算コストが高いという課題がありました。
*   **固定されたデータセットとトレーニングスケジュールの限界:** 多くの既存手法は、固定されたデータセットやトレーニングスケジュールに依存しており、データ分布が不均一または偏っている場合に最適とは言えませんでした。特に難易度の高い問題ばかり、あるいは簡単な問題ばかりといった場合に性能が頭打ちになることがありました。

## 2. どのようなアプローチでそれを解決しようとしたか

本研究では、**AdaRFT（Adaptive Curriculum Reinforcement Finetuning）** という新しいRFT手法を提案し、これらの課題を解決しようとしました。AdaRFTは、適応的なカリキュラム学習に基づいており、トレーニングセットの難易度をモデルのスキルレベルに合わせて動的に調整します。

具体的なアプローチは以下の通りです。

1.  **問題難易度の事前設定:** データセット内の各問題に、人間のアノテーションまたはモデルの成功率に基づいて難易度スコアを事前割り当てします。
2.  **ターゲット難易度の動的調整:** モデルの最近の報酬信号に基づいて、ターゲット難易度を維持・調整します。モデルの性能が向上すればターゲット難易度を上げ、性能が低下すれば下げます。
3.  **適応的な問題選択:** 各ステップで、ターゲット難易度に最も近い難易度の問題を選択してモデルをファインチューニングします。これにより、モデルは常に挑戦的でありながら解決可能なタスクでトレーニングされます。

このアプローチにより、AdaRFTは標準的なRFTアルゴリズム（PPOなど）に軽量な拡張を加えるだけで、報酬関数やモデルアーキテクチャを変更せずに、トレーニングの効率と精度を向上させることが可能になります。

## 3. 結果、何が達成できたのか

AdaRFTの実験結果は、以下の点で優れた性能を示しました。

*   **トレーニング効率の向上:** トレーニングステップ数を最大で2倍削減することができました。これは、計算資源の節約に大きく貢献します。
*   **精度の向上:** 複数のデータ分布とモデルサイズで、精度が大幅に向上しました。特に、偏ったデータ分布での効果が顕著でした。
*   **スケーラビリティの向上:** 軽量な拡張であるため、既存のRFTフレームワークに容易に組み込むことができ、スケーラブルなRFTの実現に貢献します。
*   **より高速な収束:** モデルがより速く収束するようになりました。
*   **計算効率の向上:** 全体的なトレーニングスループットが向上しました。

これらの結果から、AdaRFTは構造化された推論タスクにおいて、より効率的で効果的なRFTフレームワークを提供できることが示されました。

## 4. Limitationや問題点は何か

AdaRFTにはいくつかの制限事項と潜在的な問題点があります。

*   **難易度推定の計算コスト:** 論文では、タスクの難易度を推定するために、各問題に対してモデルを128回試行し、その成功率を難易度のプロキシとして使用しています。これは計算コストが高く、より洗練された代替手段、例えば、モデルベースの難易度推定（応答の長さ、推論ステップ数、不確実性信号などの特徴から難易度を予測する軽量なモデル）が望ましいです。
*   **カリキュラムスケジュールの適応性:** 損失傾向、信頼度、勾配分散などのより豊富なシグナルを使用したり、モデルやオプティマイザをカリキュラムと共同で適応させると、さらにパフォーマンスが向上する可能性があります。
*   **設定のバランス:** バランスの取れた設定や高容量のモデルでは、カリキュラム学習の効果が薄れる場合があるため、いつカリキュラム学習が収益逓減になるかを理解することが重要です。
*   **ハイパーパラメータの調整:** 論文中では、ターゲット報酬`beta`、感度パラメータ`alpha`、ステップサイズ`eta`などのハイパーパラメータを検証セットで調整する必要があると述べています。これらのハイパーパラメータは、特定のタスクやモデルアーキテクチャに合わせて慎重に調整する必要があります。
*   **データセットの偏り:** AdaRFTの効果は、データセットの偏りに大きく依存します。偏ったデータセットでは効果を発揮しやすいですが、バランスの取れたデータセットでは効果が限定的です。
*   **難易度スコアの信頼性:** 問題の難易度スコアが正確でない場合、AdaRFTの効果が損なわれる可能性があります。難易度スコアの信頼性を検証し、必要に応じて修正する必要があります。

## 5. 技術的な詳細について

AdaRFTは、標準的な強化学習アルゴリズム（PPOなど）の上に構築された、軽量なカリキュラムスケジューラです。主な技術的要素は以下の通りです。

1.  **難易度スコア:** 各トレーニングサンプル（数学の問題）には、事前に計算された難易度スコア`d_i`が割り当てられています。このスコアは、人間の専門家によるアノテーションや、モデルの経験的な成功率から算出できます。
2.  **ターゲット難易度:** トレーニング中に、ターゲット難易度`T`を維持します。これは、モデルが現在トレーニングすべき問題の難易度の目標値を表します。
3.  **問題選択:** 各トレーニングステップで、以下の手順で問題をバッチ`X`として選択します。

    ```python
    # 各問題のターゲット難易度との絶対差を計算
    delta = [abs(d_i - T) for d_i in dataset]
    # 差が最小の問題をB個選択
    X = select_top_B_problems(dataset, delta)
    ```

4.  **報酬計算:** 選択されたバッチ`X`について、モデル`π_θ`によって解`G`を生成し、報酬`R`を計算します。正解の場合は報酬1、不正解の場合は報酬0とします。

    ```python
    G = policy(X) # モデルによる解答の生成
    R = [1 if is_correct(G_i) else 0 for G_i in G] # 報酬の計算
    R_avg = sum(R) / len(X) # 平均報酬
    ```

5.  **ポリシー更新:** 強化学習アルゴリズム`A`（PPOなど）を使用して、ポリシー`π_θ`を更新します。

    ```python
    pi_theta = A(pi_theta, X, G, R)
    ```

6.  **ターゲット難易度更新:** ターゲット難易度`T`を、平均報酬`R_avg`に基づいて更新します。

    ```python
    # 難易度調整のステップサイズ
    eta = 0.01 # 例
    # 報酬感度パラメータ
    alpha = 1.0 # 例
    # 目標報酬
    beta = 0.5 # 例
    
    # tanh関数で調整された難易度変化量
    delta_T = eta * tanh(alpha * (R_avg - beta))
    
    # クリップ関数で難易度変化量を制限
    T_prime = clip(T + delta_T, d_min, d_max)
    T = T_prime
    ```

    ここで、`tanh`は双曲線正接関数であり、`clip`は値を範囲`[d_min, d_max]`に制限する関数です。`eta`, `alpha`, `beta`はハイパーパラメータであり、それぞれ難易度調整のステップサイズ、報酬感度、目標報酬を表します。

# Unified World Models: Coupling Video and Action Diffusion for Pretraining on Large Robotic Datasets

[View Paper](http://arxiv.org/abs/2504.02792v1)

## 1. 既存研究では何ができなかったのか

既存のロボット学習研究は、主に以下の点で限界がありました。

*   **高品質な専門家のデモンストレーションへの依存:** Imitation Learning (IL) は有望ですが、大規模ロボットモデルの構築には、高品質なデモンストレーションデータが必要で、その収集にはコストと時間がかかります。
*   **行動アノテーションの必要性:** 大量のビデオデータは利用可能ですが、多くの場合、行動アノテーションが付与されていないため、既存のIL手法では直接活用できません。
*   **時間的ダイナミクスの明示的な学習の欠如:** 多くのIL手法は状態から行動へのマッピングを学習するだけで、デモンストレーションやビデオに自然に存在する時間的なダイナミクスを明示的に捉えません。
*   **ポリシーとワールドモデルの分断:** ポリシー学習とワールドモデリングは別々の分野として研究されてきましたが、互いに補完し合う可能性があります。
*   **マルチモーダルデータの効果的な統合の難しさ:** 既存の joint video-action モデルでは、異なるモダリティ間の因果関係の理解が不十分な場合があります。また、ビデオとアクションの情報を効果的に共有できていない場合があります。

## 2. どのようなアプローチでそれを解決しようとしたか

本論文では、Unified World Models (UWM) という新しいフレームワークを提案し、これらの課題を解決しようとしました。

*   **ビデオと行動データの一元的な活用:** UWM は、行動データとビデオデータを両方活用できるフレームワークです。
*   **行動拡散とビデオ拡散の統合:** UWM は、統一されたTransformerアーキテクチャ内で行動拡散プロセスとビデオ拡散プロセスを統合します。各モダリティは独立した拡散タイムステップによって制御されます。
*   **柔軟な推論:** 各拡散タイムステップを制御することで、ポリシー、順ダイナミクス、逆ダイナミクス、ビデオジェネレーターを柔軟に表現できます。
*   **行動不要なビデオデータからの学習:** モダリティ固有の拡散タイムステップを独立して制御することで、行動アノテーションのないビデオデータからの学習を容易にします。
*   **因果関係の学習:** モデルは、可能なすべての周辺分布と条件付き分布を学習することで、行動と画像間の因果関係を理解します。

具体的には、以下のようなアプローチをとっています。

1.  **モデルアーキテクチャ:**
    *   画像(o), 行動(a), 次の画像(o') の３つを扱うdiffusion modelを構築
    *   画像と行動それぞれに拡散noiseを加えるstep数 `t_a`, `t_o` を用意。これらを独立に操作できるようにする
    *   モデルの中身はTransformerで、画像、行動をそれぞれembeddingに変換したものを入力とする

2.  **学習:**
    *   データセットから `(o, a, o')` のtupleをサンプル
    *   `t_a`, `t_o` をそれぞれ `0` から `T` の間でランダムにサンプル
    *   以下を最小化するように学習
        ```python
        def diffusion_loss(model, o, a, o_prime, t_a, t_o):
            a_t = add_noise(a, t_a) # 行動aにノイズを加える
            o_prime_t = add_noise(o_prime, t_o) # 次の画像o'にノイズを加える

            # モデルに o, a_t, o'_t, t_a, t_o を入力し、ノイズを予測させる
            epsilon_a_hat, epsilon_o_prime_hat = model(o, a_t, o_prime_t, t_a, t_o)

            # 予測されたノイズと実際のノイズとの誤差を計算
            loss_a = mse_loss(epsilon_a_hat, noise_a)
            loss_o = mse_loss(epsilon_o_prime_hat, noise_o_prime)

            # 行動と画像の損失を重み付けして合計
            loss = w_a * loss_a + w_o * loss_o
            return loss
        ```
    *   行動データがないビデオデータも学習に使える。その場合は `t_a = T` とし、行動 `a` はランダムなノイズで埋める。

3.  **推論:**
    *   `t_a`, `t_o` を固定することで、様々な推論が可能になる
        *   `t_o = T`: 行動生成 (Policy)
        *   `t_a = T`: ビデオ生成
        *   `t_a = 0`: 順ダイナミクスモデル
        *   `t_o = 0`: 逆ダイナミクスモデル
    *   例えば、行動生成の場合、`t_o`を`T`に固定した状態で、行動のノイズを除去していくことで、行動を生成する

## 3. 結果、何が達成できたのか

UWM は、シミュレーションと実世界の実験を通じて、以下の成果を達成しました。

*   **大規模なマルチタスクロボットデータセットでの効果的な事前学習:** UWM は、ダイナミクス予測と行動予測の両方で、大規模なマルチタスクロボットデータセットで効果的な事前学習を可能にし、Imitation Learningよりも汎化性と堅牢性の高いポリシーを実現しました。
*   **行動アノテーションのないビデオデータからの学習:** UWM は、モダリティ固有の拡散タイムステップを独立して制御することで、行動アノテーションのないビデオデータからの学習を自然に促進し、ファインチューニングされたポリシーのパフォーマンスをさらに向上させました。
*   **汎用的な意思決定モデル:** UWM は、ポリシー、ダイナミクスモデル、ビデオ予測器、逆モデルとして機能する、シンプルで統一された拡散モデルを提供します。
*   **ロバスト性と汎化性の向上:** UWM は、標準的な Imitation Learning と比較して、改善されたポリシーにつながります。

    *   統一されたアーキテクチャにより、アクションとピクセル間の特徴共有が可能になり、同じデータから追加の教師あり信号が得られます。
    *   モデルは、すべての組み合わせの周辺分布と条件付き分布をキャプチャし、アクションと画像の間の因果関係を理解します。
    *   モデルは、アクションフリービデオなどのより広範なデータモダリティから学習できます。

*   **実ロボットタスクでの性能向上:** 複数の実ロボットタスクにおいて、UWMが既存手法よりも高い成功率を達成しました。特に、分布外（OOD）の条件下でもロバスト性を示しました。

## 4. Limitationや問題点は何か。本文で言及されているものの他、あなたが考えるものも含めて

UWM には、いくつかの Limitation と問題点があります。

*   **大規模な人間のビデオからの学習の欠如:** 提案されたモデルは、まだ大規模な人間のビデオから学習し、エンボディメントギャップを埋めることができません。
*   **フォワードダイナミクスの予測のアーティファクト:** UWM は行動予測を改善しますが、フォワードダイナミクスの再構成にはアーティファクトが含まれる場合があり、このモデルを使用した計画の有効性を低下させる可能性があります。
*   **計算コスト:** 拡散モデルは一般的に計算コストが高く、UWM も例外ではありません。特に、大規模なデータセットや複雑なタスクでは、トレーニングに時間がかかる可能性があります。
*   **ハイパーパラメータの調整:** UWM はハイパーパラメータに対して比較的安定していますが、高度にマルチモーダルなデータセットで事前学習を行う場合は、レジスタの数を増やすとパフォーマンスが向上する可能性があります。新しいデータセットでは、デフォルトのハイパーパラメータを最初に試してから、レジスタの数を調整することをお勧めします。
*   **シミュレーションと現実のギャップ:** シミュレーション実験では改善が見られるものの、実世界の実験ほどではありません。これは、現在のシミュレーションが現実世界よりも単純なダイナミクスを持っていることが原因である可能性があります。

### 個人的に考える問題点

*   **Explorationの問題:** imitation learningをベースにしているため、学習データにない状態への対応が難しい。
*   **長期的な計画:** 現状では、次の状態を予測するフォワードダイナミクスの精度が十分ではないため、長期的な計画には向いていない可能性がある。
*   **タスクの複雑性:** 論文中で扱っているタスクは、比較的単純なマニピュレーションタスクに限られている。より複雑なタスクや、複数のステップを伴うタスクへの適用は今後の課題。

## 5. 技術的な詳細について。技術者が読むことを想定したトーンで

UWM は、Diffusion Transformer をベースにしており、AdaLN (Adaptive Layer Normalization) を用いて条件付けを行っています。以下に技術的な詳細を示します。

1.  **モデルアーキテクチャ:**
    *   入力:
        *   現在の観測 `o` (複数のカメラからのフレームスタック)
        *   行動 `a_t_a` (ノイズが加えられた行動)
        *   次の観測 `o'_t_o'` (ノイズが加えられた次の観測)
        *   拡散タイムステップ `t_a`, `t_o'` (行動と観測それぞれ)
    *   処理:
        *   **画像特徴抽出:** ResNet-18 を用いて、各カメラビューの各フレームから特徴を抽出します。ImageNet で事前学習された重みで初期化し、学習中に更新します。

## 1. 既存研究では何ができなかったのか

既存のカスタマイズ画像生成研究は、主に以下の2つの課題に直面していました。

*   **データスケーラビリティの限界:** 単一の被写体を対象としたデータセットから、複数の被写体を含むデータセットへの拡張が困難でした。多様なポーズ、場所、サイズなどの属性を持つ被写体のバリエーションを網羅したデータを取得することが現実的ではありませんでした。既存の手法では、被写体のバリエーションが限られた実画像を使用するか、品質の低い合成データを使用しており、被写体の類似性とテキストの制御性の間でトレードオフが生じていました。
*   **被写体拡張性の限界:** ほとんどの手法が単一の被写体の生成に焦点を当てており、複数の被写体を扱うシナリオへの適用が困難でした。

これらの課題は、カスタマイズされたモデルのスケーラビリティを制限し、テキストによる制御性を維持しながら視覚的な被写体の制御を増加させることを困難にしていました。

## 2. どのようなアプローチでそれを解決しようとしたか

本研究では、上記の課題を解決するために、モデルとデータの協調進化を可能にする新しいパラダイムを提案しました。このパラダイムでは、制御性の低い先行モデルが、より制御性の高い後続のモデルのためのより良いカスタマイズデータを体系的に合成します。具体的には、以下の2つの主要な要素で構成されています。

*   **体系的な合成データキュレーションフレームワーク:** 制御性の低いモデルからの知識蒸留を利用して、高品質で高解像度のペアのカスタマイズデータを生成します。これには、シングル被写体からマルチ被写体へのインコンテキスト生成への移行と、微調整されたアンサンブルフィルタリングによる前例のない高解像度、高品質のペアのカスタマイズデータをキュレーションするための多段階フィルタリングメカニズムを組み合わせたプログレッシブな合成パイプラインが含まれます。
*   **汎用的なカスタマイズモデルフレームワーク (UNO):** 階層的な制御性適応を可能にし、さまざまな程度の制御性でシームレスなスケーラビリティを保証します。具体的には、Diffusion Transformer (DiT)のマルチ条件コンテキスト機能を活用し、プログレッシブクロスモーダルアラインメントとユニバーサルロータリーポジションエンベディング（UnoPE）で構成されています。

## 5. 技術的な詳細について

提案手法の中核は、並列デコードを可能にする特殊なアテンションマスクです。

以下に、並列デコードの疑似コードを示します。

```python
def parallel_decode(model, input_sequence, attention_mask):
  """
  並列デコードを行う関数

  Args:
    model: 推論モデル
    input_sequence: 入力シーケンス
    attention_mask: 並列デコード用のアテンションマスク

  Returns:
    output_sequence: 出力シーケンス
  """

  # 現在のシーケンス長
  current_length = len(input_sequence)

  # 並列にデコードするトークン数 (例: 4)
  parallel_tokens = 4

  # 出力シーケンスを初期化
  output_sequence = input_sequence[:] # deepcopy

  # モデルの forward pass
  outputs = model(
      input_ids = torch.tensor([input_sequence]), # 仮に PyTorch を使用
      attention_mask = torch.tensor([attention_mask])
  )

  # logits を取得
  logits = outputs.logits

  # 最後の parallel_tokens 個の logits を選択
  parallel_logits = logits[:, current_length-1 : current_length + parallel_tokens -1, :]

  # 各トークンに対して、最も確率の高いトークンを選択
  predicted_tokens = torch.argmax(parallel_logits, dim=-1)[0].tolist()

  # 出力シーケンスに追加
  output_sequence.extend(predicted_tokens)

  return output_sequence
```

**注意点:**

*   `attention_mask` は、各トークンが参照すべきトークンを制御します。並列デコードでは、各トークンが、自分より前のトークンだけでなく、同じステップでデコードされる他のトークンも参照できるように設計する必要があります。
*   モデルの出力 (`logits`) から、並列にデコードされたトークンに対応する部分のみを選択する必要があります。
*   並列デコードするトークン数は、タスクやモデルの構造に合わせて調整する必要があります。

# COIG-P: A High-Quality and Large-Scale Chinese Preference Dataset for Alignment with Human Values

[View Paper](http://arxiv.org/abs/2504.05535v1)

## 1. 既存研究では何ができなかったのか

既存の中国語のPreferenceデータセットは、以下の点で不十分でした。

*   **規模の小ささ:** データセットのサイズが小さく、大規模言語モデル（LLM）の訓練には不十分でした。
*   **ドメインの偏り:** 特定のドメインに偏っており、多様なタスクをカバーできていませんでした。例えば、Zhihuのような単一のソースから派生したデータセットがありました。
*   **厳格なデータ検証の欠如:** データのフィルタリングや品質管理が不十分で、信頼性や妥当性に疑問がありました。
*   **人手によるアノテーションへの依存:** 指示や応答のラベリングに人手を介していたため、データセットのスケーラビリティが制限されていました。人手によるアノテーションは時間がかかり、コストも高くなります。また、アノテーションの一貫性の問題もありました。
*   **LLMによるスコアリングの偏り:** LLMを使用して応答をスコアリングする場合、単一のLLMに依存している既存研究があり、偏りが生じる可能性がありました。複数のLLMを使用する研究でも、応答に対して異なる側面からスコアを付与するため、高品質なChosen-Rejectedペアの選択が困難でした。

## 2. どのようなアプローチでそれを解決しようとしたか

この論文では、上記の問題を解決するために、以下の様なアプローチを取りました。

*   **LLMベースの自動アノテーションパイプラインの設計:** 人手を介さずに、LLMのみで中国語のPreferenceデータセットを構築するパイプラインを設計しました。
*   **大規模なクエリデータの収集とフィルタリング:** 92k件の高品質な中国語クエリを収集し、多様性を確保するためにフィルタリングを行いました。質問応答プラットフォーム、管理能力試験、英語データセットの翻訳など、複数のソースからクエリを収集しました。フィルタリングプロセスには、質問の多様性を確保するためのSentenceBERTによるセマンティック類似性計算、質問がユーザーの一般的な質問を反映しているかどうかを評価するためのLLMによるスコアリング、および形式が整っているかどうかを検証するためのルールベースのフィルタリングが含まれていました。
*   **多様なLLMによる応答生成とスコアリング:** 複数のオープンソースおよびクローズドソースのLLMを使用して、各クエリに対する多様な応答を生成しました。そして、別のLLM群を使用して、これらの応答をスコアリングし、Chosen-Rejectedの応答ペアを作成しました。応答のスコアリングには、ドメインに適したプロンプトを使用しました。
*   **Chosen-Rejectedペアのフィルタリング:** スコアの差が一定の閾値（2.0）を超えるChosen-Rejectedペアのみを保持することで、データセットの品質を向上させました。
*   **中国語Reward Model（CRM）の訓練:** LLMによるスコアリングのオーバーヘッドを削減するために、8Bサイズの中国語Reward Model（CRM）を訓練しました。CRMの訓練には、COIG-Pデータセットの半分を使用し、残りの半分でテストしました。
*   **中国語Reward Benchmark（CRBench）の構築:** CRMの評価のために、高品質な中国語Reward Benchmark（CRBench）を構築しました。CRBenchのデータは、クリーニング、再構成、および人間による検証を経て、その品質と多様性を確保しました。
*   **AlignBenchでの評価:** COIG-Pで訓練したLLMの性能を、AlignBenchを用いて評価しました。
*   **CRMの評価:** CRBenchを用いて、CRMの性能を評価しました。また、COIG-Pのテスト分割を用いて、CRMが低品質なサンプルを識別する能力をGPT-4oと比較しました。

## 3. 結果、何が達成できたのか

この研究によって、以下の成果が得られました。

*   **COIG-Pデータセットの構築:** 1,009k件の中国語Preferenceペアを含む、大規模で高品質なCOIG-Pデータセットを構築しました。データセットは、チャット、コード、数学、論理、小説、ロールプレイングの6つの多様なドメインをカバーしています。
*   **LLMの性能向上:** COIG-Pで訓練されたLLM（Qwen2/2.5、Infinity-Instruct-3M-0625シリーズなど）は、AlignBenchにおいて2%から12%の性能向上が見られました。
*   **CRMの訓練と評価:** 8Bサイズの中国語Reward Model（CRM）を訓練し、CRBenchにおいて強力でロバストなスコアリング能力を持つことを示しました。
*   **CRMの低品質サンプル識別の実証:** CRMがCOIG-Pのテスト分割において、GPT-4oに匹敵する品質で低品質なサンプルを識別できることを実験的に示しました。CRMを使用することで、LLMによるスコアリングと比較して、計算コストを大幅に削減できました。
*   **既存の中国語Preferenceデータセットの改善:** COIG-Pは、既存の他の中国語Preferenceデータセットよりも大幅に優れたパフォーマンスを示しました。他のデータセットとは対照的に、COIG-Pでトレーニングされたモデルは、すべてのサブタスクで一貫してパフォーマンスが向上しました。
*   **データセットの公開:** COIG-Pデータセットと関連コードを公開し、研究コミュニティに貢献しました。（[https://github.com/multimodal-art-projection/COIG-P](https://github.com/multimodal-art-projection/COIG-P)）

## 4. Limitationや問題点は何か

この研究には、以下の様なLimitationや問題点が考えられます。

*   **データセットの偏り:** COIG-Pは多様なドメインをカバーしていますが、特定のドメインやタスクに偏りがある可能性は否定できません。例えば、特定のLLMが生成しやすい応答や、特定のトピックに関するクエリが過剰に含まれている可能性があります。
*   **LLMによるスコアリングの限界:** LLMによるスコアリングは、完全な客観性や人間の価値観との完全な一致を保証するものではありません。LLMは、自身の学習データやアーキテクチャに起因するバイアスを持つ可能性があります。
*   **CRMの汎化性能:** CRMはCRBenchにおいて高い性能を示していますが、他の未知のデータセットやタスクに対する汎化性能は不明です。CRMの訓練データに過度に適合している場合、新しいデータに対しては性能が低下する可能性があります。
*   **閾値の選択:** Chosen-Rejectedペアのフィルタリングにおける閾値（2.0）は、経験的に決定されたものであり、最適な値である保証はありません。他の閾値を選択した場合、異なる結果が得られる可能性があります。
*   **人手による評価の限界:** データセットの品質を評価するために人手による評価を実施しましたが、評価者の主観やバイアスが影響する可能性があります。
*   **計算リソース:** LLMの訓練や評価には多大な計算リソースが必要であり、再現性や拡張性を妨げる可能性があります。
*   **ドメイン知識の不足:** 特に、数学、コード、論理的推論などのタスクでは、LLMが生成する応答の正しさを判断するために、特定の分野の専門知識が必要となる場合があります。専門知識が不足している場合、不正確なChosen-Rejectedペアがデータセットに含まれる可能性があります。
*   **安全性と倫理:** データセットに含まれるコンテンツが、安全性や倫理的な観点から問題がないか、十分な検証が必要です。特に、ロールプレイングや小説などのドメインでは、不適切なコンテンツが含まれるリスクがあります。

## 5. 技術的な詳細について

*   **クエリ収集とフィルタリング:**

    1.  **多様なソースからのクエリ収集:** 中国のQ&Aプラットフォーム（Baidu Zhidao）、中国の管理能力試験、英語のオープンソースデータセット（HotpotQAなど）を翻訳したものなど、多様なソースからクエリを収集。

    3.  **LLMによるスコアリング:** LLMを使用してクエリをスコアリングし、一般的なユーザーが質問する可能性のある質問を反映していないクエリを削除。
    4.  **ルールベースのフィルタリング:** 形式が整っていないクエリを削除。
*   **応答生成とスコアリング:**

    1.  **多様なLLMによる応答生成:** 複数のLLM（オープンソースおよびクローズドソース）を使用して、各クエリに対する多様な応答を生成。
    2.  **ドメインに適したプロンプト:** 応答のスコアリングには、ドメインに適したプロンプトを使用。
    3.  **LLMによるスコアリング:** 別のLLM群を使用して応答をスコアリング。
*   **Chosen-Rejectedペアの作成とフィルタリング:**

    1.  **ペアの作成:** 各クエリに対して2つの応答をランダムにサンプリングし、Chosen-Rejectedペアを作成。
    2.  **スコア差によるフィルタリング:** スコアの差が閾値（2.0）を超えるペアのみを保持。

        ```python
        def filter_pairs(pairs, threshold=2.0):
            filtered_pairs = []
            for pair in pairs:
                chosen_score = pair['chosen_score']
                rejected_score = pair['rejected_score']
                if chosen_score - rejected_score > threshold:
                    filtered_pairs.append(pair)
            return filtered_pairs
        ```

        ```python
        import torch
        import torch.nn.functional as F

        def bradley_terry_loss(chosen_rewards, rejected_rewards):
            # chosen_rewards と rejected_rewards は、それぞれの応答に対する報酬値のテンソル
            preferences = chosen_rewards - rejected_rewards  # 選好度を計算
            loss = -F.logsigmoid(preferences).mean()  # BT損失を計算
            return loss
        ```

# CrossWordBench: Evaluating the Reasoning Capabilities of LLMs and LVLMs with Controllable Puzzle Generation

[View Paper](http://arxiv.org/abs/2504.00043v1)

## 1. 既存研究では何ができなかったのか

既存の研究は、大規模言語モデル（LLM）および大規模視覚言語モデル（LVLM）の推論能力の評価において、以下の点で限界がありました。

*   **テキストベースまたは視覚言語理解に偏重:** 既存の評価フレームワークは、テキストベースの推論または視覚言語理解のどちらかに焦点を当てており、テキストと視覚的な制約間の動的な相互作用が不足していました。
*   **マルチモーダル推論能力の評価の欠如:** 現実世界の問題解決を特徴づけるテキストと視覚的な制約間の動的な相互作用を必要とするタスク、特に、マルチモーダル推論能力を評価することが困難でした。
*   **既存のクロスワードデータセットの制約:** 既存のクロスワードデータセットは、静的で著作権で保護されたオンラインニュースソースに依存しており、テキスト中心の定式化を採用しているため、視覚的な構造を無視していました。
*   **LVLM評価のためのクロスワードパズルの拡張の欠如:** 既存のデータセットとアプローチは、クロスワードパズルを質問応答（QA）タスクとして定式化しているため、制約ベースの本質を見落としていました。さらに、クロスワードのグリッドの視覚的な性質にもかかわらず、テキストベースのタスクとして扱っており、LVLMの評価に拡張する上でのギャップが残っていました。
*   **マルチモーダルデータセットの不足:** マルチモーダル推論の進化に伴い、検証可能な報酬で学習するための適切なマルチモーダルデータセットの不足が課題として残っていました。

## 2. どのようなアプローチでそれを解決しようとしたか

本研究では、上記の課題を解決するために、以下のようアプローチを採用しました。

*   **CrossWordBenchの導入:** テキストベースの手がかりと視覚的なグリッド構造からの交差制約の両方に対するマルチモーダルな準拠を必要とするタスクであるクロスワードパズルを媒体として、LLMとLVLMの両方の推論能力を評価するために設計されたベンチマークを導入しました。
*   **制御可能なパズル生成フレームワークの活用:** 複数のフォーマット（テキストと画像）でパズルを生成し、直接パズルを解くことからインタラクティブモードまで、さまざまな評価戦略を提供する制御可能なパズル生成フレームワークを活用しました。パズル生成は以下の3つのソースから行われます。
    1.  多言語の単語と手がかりのペアを公開リポジトリから収集
    2.  辞書ベースの定義を使用
    3.  既存のベンチマーク（CommonsenseQAなど）から、回答がオープンエンドまたは制約のない質問と回答のペアを適合
*   **評価モード:**
    *   **直接パズルを解くモード:** ゼロショットのChain-of-Thought（CoT）プロンプトを使用して1ラウンドの応答を生成
    *   **インタラクティブモード:** ステップバイステップのパズルを解くために、グリッドジェネレーターを呼び出して、フォローアップのための中間的な視覚的な出力を提供し、関数呼び出しを使用するエージェントを評価するための基盤として機能
*   **構造的制約の重視:** 問題解決における構造的制約の重要性を強調するため、完全に近い状態のベンチマークから派生したパズルを使用しました。

## 3. 結果、何が達成できたのか

この研究の結果、以下の成果が得られました。

*   **LLMの推論能力の評価:** 推論LLMは、交差する文字の制約を効果的に活用することにより、非推論モデルを大幅に上回ることが示されました。特に、o3-miniは高いICR (Internal Consistency Ratio)を達成し、グリッドの制約を解釈し、適用する強力な能力を示しました。
*   **LVLMの課題の特定:** LVLMはタスクに苦戦し、パズルを解くパフォーマンスとグリッド解析の精度との間に強い相関関係があることが示されました。LVLMは特に垂直方向（下向き）の単語抽出におけるOCRに苦戦し、単語の向きに体系的なバイアスがあることが明らかになりました。また、思考モードを有効にすると、Claude-3-7-Sonnetのグリッド解析のパフォーマンスが低下し、パズルを解くパフォーマンスの低下と一致することがわかりました。
*   **CrossWordBenchの有効性の実証:** 飽和状態のベンチマークから派生したパズルでさえ、依然として課題があることが示され、厳密な推論評価における構造的複雑さの必要性が強調されました。CrossWordBenchは、LLMとLVLMの推論能力を評価するための効果的なアプローチを提供し、将来の評価のためのマルチモーダル制約タスクを作成するための新しい方法を提供しました。
*   **マルチモーダルRLトレーニングの可能性:** クロスワードパズルが本質的な検証可能性とマルチモーダルな性質のために有望な代替手段を提供し、CrossWordBenchのフレームワークがこのギャップに対処するための基盤として役立つと主張しました。

## 4. Limitationや問題点は何か。本文で言及されているものの他、あなたが考えるものも含めて

### 本文で言及されているもの
*   **LVLMのOCRの制限:** LVLMは垂直方向の単語抽出におけるOCRに苦戦することが示されました。
*   **思考モードのLVLMへの影響:** 思考モードを有効にすると、Claude-3-7-Sonnetのグリッド解析のパフォーマンスが低下し、パズルを解くパフォーマンスの低下と一致することがわかりました。

### その他考えられるもの
*   **データ汚染の可能性:** ワード-手がかりペアの収集元によっては、モデルの事前学習データにデータが含まれている可能性があり、評価の信頼性に影響を与える可能性があります。
*   **評価指標の限界:** ICRは交差部分の一貫性を評価する上で役立ちますが、パズル全体の正解率を完全に捉えているとは言えません。より包括的な評価のために、他の指標（手がかりの解釈の正確さなど）を考慮することもできます。
*   **パズル生成の制約:** パズル生成パイプラインが完全に自動化されているにもかかわらず、生成されるパズルの難易度と創造性には制限がある可能性があります。人間の専門家が作成したパズルと比較して、手がかりがより直接的で、複雑さが少ない可能性があります。
*   **モデルの一般化の限界:** CrossWordBenchは推論能力を評価するための貴重なツールですが、結果が他のタスクやドメインにどれだけ一般化できるかは不明です。
*   **評価モードの限界:** 直接パズルを解くモードでは、CoTプロンプトの品質に結果が大きく依存します。インタラクティブモードでは、会話履歴の制限により、モデルの長期的な推論能力を完全に評価できない可能性があります。
*   **マルチモーダルRLトレーニングの課題:** クロスワードパズルを使用したマルチモーダルRLトレーニングは有望ですが、適切な報酬関数の設計や、訓練データの多様性を確保する上での課題が残っています。
*   **グリッドの複雑さの制御:** グリッドのサイズと交差する文字の数がパズルの難易度に影響を与えることは示されていますが、グリッドの構造（対称性、単語の配置など）の他の側面がモデルのパフォーマンスにどのように影響するかは、まだ十分に調査されていません。

## 5. 技術的な詳細について。技術者が読むことを想定したトーンで

CrossWordBenchの技術的な詳細は以下の通りです。

*   **パズル生成パイプライン:**
    1.  **データ収集:**
        *   多言語のワード-手がかりペアは、公開されているオンラインリポジトリから収集します。
        *   標準的な英語の単語と、NLTK WordNetからの辞書の定義を使用します。
        *   CommonsenseQAなどの既存のベンチマークから、単語の回答を持つ質問と回答のペアを抽出します。
    2.  **グリッド生成:**
        *   収集されたワード-手がかりペアに基づいて、自動パイプラインがグリッドを生成します。
        *   グリッドサイズ（例：7x7、14x14）と単語の配置を制御することで、パズルの難易度を調整できます。
        *   交差する文字の数を最大化するように単語を配置するアルゴリズムを使用します。
    3.  **フォーマット:** パズルは、LLMとLVLMの両方に対応するために、テキスト形式と画像形式で生成されます。

*   **モデル評価:**
    1.  **プロンプト:**
        *   **ゼロショットCoTプロンプト:** モデルにステップバイステップの推論を促すために使用されます。
        *   **画像プロンプト:** LVLMの場合、グリッドと手がかりが画像に埋め込まれます。LLMの場合、グリッドは2Dバイナリ配列（0は空のセル、1は塗りつぶされたセル）として表現され、テキストの手がかりの前に追加されます。
        *  **思考モードプロンプト:** モデルに過去の回答を再検討するように促すためのフォローアップクエリを手動で作成します。
    2.  **出力解析:**
        *   `o3-mini`の構造化された出力機能を利用して、モデルの生の応答をJSON形式に変換します。
        *   動的なPydanticモデルを生成して、出力構造を定義します。
    3.  **評価指標:**
        *   **Word Correctness Ratio (WCR):** 正しく解かれた単語の割合。

            ```python
            def calculate_wcr(predicted_answers, reference_answers):
                correct_count = 0
                for word in reference_answers["across"] + reference_answers["down"]:
                    if predicted_answers.get(word, "") == reference_answers[word]["answer"]:
                        correct_count += 1
                return correct_count / len(reference_answers["across"] + reference_answers["down"])
            ```

        *   **Letter Correctness Ratio (LCR):** 正しい文字の配置の割合。

            ```python
            def calculate_lcr(predicted_answers, reference_answers):
                correct_letters = 0
                total_letters = 0
                for word in reference_answers["across"] + reference_answers["down"]:
                    predicted_word = predicted_answers.get(word, "")
                    reference_word = reference_answers[word]["answer"]
                    min_length = min(len(predicted_word), len(reference_word))
                    max_length = max(len(predicted_word), len(reference_word))

                    for i in range(min_length):
                        if predicted_word[i] == reference_word[i]:
                            correct_letters += 1
                    total_letters += max_length
                return correct_letters / total_letters
            ```

        *   **Internal Consistency Ratio (ICR):** 交差部分でのモデルの回答の内部一貫性。

            ```python
            def calculate_icr(predicted_answers, reference_answers):
                intersections = find_intersections(reference_answers) # 関数find_intersections は交差部分を見つける必要があります
                correct_intersections = 0
                for a, d, j, k in intersections:
                    word_a = predicted_answers.get(a, "")
                    word_d = predicted_answers.get(d, "")
                    if word_a and word_d and len(word_a) > j and len(word_d) > k:
                        if word_a[j] == word_d[k]:
                            correct_intersections += 1
                return correct_intersections / len(intersections) if intersections else 0
            ```

*   **インタラクティブモード:**
    *   LVLMがステップバイステップでパズルを解くことができるようにします。
    *   モデルが回答を提供するたびにグリッド画像を更新するために、外部関数を使用します。
    *   モデルの最初のエラーの前に正しく解かれた単語の数を定量化するために、Initial Solution Step（ISS）のメトリックを使用します。

# Skywork R1V: Pioneering Multimodal Reasoning with Chain-of-Thought

[View Paper](http://arxiv.org/abs/2504.05599v1)

## 1. 既存研究では何ができなかったのか

既存のVision-Languageモデル（VLM）は、記述的なタスク（例えば、画像に対する文脈的に適切な説明文の生成）では優れていますが、幾何学的な証明や科学的な問題解決など、高度な論理的推論を必要とするマルチモーダルなタスクにおいては、シングルモーダルなシステムと比較して性能が劣っていました。既存のVLMデータセットは推論能力を必要とするコンテンツが少なく、Chain-of-Thought（CoT）の例も高度な推論タスクには不十分でした。そのため、これらのデータセットでVLMをトレーニングすると、マルチモーダルな推論能力が強化されるどころか、弱まる可能性がありました。

## 2. どのようなアプローチでそれを解決しようとしたか

Skywork R1Vは、以下の3つのコアとなる技術革新によって、この問題に対処しようとしました。

1.  **推論能力を持つLLMの効率的なマルチモーダル転送:** 軽量な多層パーセプトロン（MLP）をビジュアルプロジェクターとして利用することで、基盤となる言語モデルやビジョンエンコーダを再トレーニングすることなく、R1シリーズのテキストモデルの推論能力をマルチモーダルなシナリオにシームレスに転送します。
2.  **ハイブリッド最適化フレームワーク:** 反復的な教師ありファインチューニング（SFT）とグループ相対ポリシー最適化（GRPO）強化学習を戦略的に統合し、効率的なクロスモーダル推論のために、視覚的およびテキスト表現を段階的に整合させます。
3.  **適応長Chain-of-Thought蒸留:** 推論チェーンの長さを動的に調整することにより、過剰な計算による熟考や考えすぎを軽減し、推論効率と推論効果を大幅に向上させます。

## 3. 結果、何が達成できたのか

Skywork R1Vは、わずか38Bのパラメータで、MMMUベンチマークで69.0、MathVistaで67.5という競争力のあるパフォーマンスを達成しました。同時に、AIMEで72.0、MATH500で94.0という優れたスコアに示されるように、堅牢なテキスト推論パフォーマンスを維持しました。さらに、MathVistaベンチマークではClaude 3.5 Sonnetを上回り、MMMUベンチマークではClaude 3.5 Sonnetに匹敵する性能を示しました。

## 4. Limitationや問題点は何か

*   **データセットのバイアス:** モデルは特定のデータセットでトレーニングされているため、別の種類のデータセットやタスクに一般化する場合、性能が低下する可能性があります。特に、推論データが不足している既存のVLMデータセットでトレーニングされている場合、性能に影響が出る可能性があります。
*   **計算コスト:** 38Bパラメータを持つモデルは比較的小規模ですが、それでも推論にはかなりの計算リソースを必要とする可能性があります。大規模なバッチサイズ、長いコンテキスト長、および複雑なChain-of-Thought推論は、すべて計算コストに寄与します。
*   **ブラックボックスな性質:** LLMの推論プロセスは依然として完全に理解されているとは言えません。これにより、モデルが特定の方法で意思決定を行う理由を理解し、デバッグすることが困難になる可能性があります。
*   **幻覚:** LLMは、事実に基づかない、または文脈に関連しない情報を生成することで知られています。これは、マルチモーダルなシナリオで、視覚的およびテキスト情報を正確に整合させることが重要な場合に問題となる可能性があります。
*   **MLPのボトルネック:** MLPアダプタは効率的な転送を可能にしますが、潜在的な情報ボトルネックにもなります。MLPアーキテクチャがビジョンエンコーダとLLMの間に必要なすべての情報を効果的に中継できない場合、これは性能に影響を与える可能性があります。
*   **GRPOの安定性:** 強化学習（RL）手法であるGRPOは、報酬関数の選択とハイパーパラメータの調整に非常に敏感です。不適切な報酬関数またはハイパーパラメータ設定は、不安定なトレーニングやサブ最適なパフォーマンスにつながる可能性があります。

## 5. 技術的な詳細について

Skywork R1Vは、R1シリーズLLMの推論能力を視覚モダリティに転送するマルチモーダル推論モデルです。主要な技術的側面は次のとおりです。

1.  **効率的なマルチモーダル転送:**

    *   **ビジュアルプロジェクター:** 軽量なMLPを使用して、ビジョンエンコーダーからの視覚的特徴をLLMの潜在空間にマッピングします。これにより、LLMまたはビジョンエンコーダーを再トレーニングせずに、視覚情報を統合できます。

    ```python
    def forward(visual_features, mlp, llm):
        # visual_features: ビジョンエンコーダからの出力
        # mlp: 多層パーセプトロンアダプタ
        # llm: 大規模言語モデル
        projected_features = mlp(visual_features)
        # 投影された特徴をLLMに入力として供給
        output = llm(projected_features)
        return output
    ```
2.  **ハイブリッド最適化フレームワーク:**

    *   **反復SFT:** モデルは、徐々に改善されたデータセットで反復的に微調整されます。各反復では、高品質のサンプル（報酬モデルによって識別される）と、以前の反復で誤分類された難しいサンプルを使用して、モデルをトレーニングします。
    *   **GRPO:** グループ相対ポリシー最適化（GRPO）を使用して、モデルの一般化をさらに強化します。GRPOは、ルールベースの報酬システム（精度報酬とフォーマット報酬）を使用して、モデルのパフォーマンスと推論の合理性を最適化します。

    ```python
    def train_step(model, data, optimizer, reward_model):
        # 順伝播
        output = model(data['input_ids'], data['visual_features'])
        # 報酬モデルから報酬を計算
        rewards = reward_model(output, data['labels'])
        # GRPO損失の計算
        loss = grpo_loss(output, rewards)
        # 逆伝播と最適化
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
        return loss
    ```
3.  **適応長Chain-of-Thought蒸留:**

    *   **QDAM:** 品質と難易度評価モジュール（QDAM）は、GPT-4oを使用して、画像-テキストクエリペアの品質と難易度を評価します。QDAMは、視覚的側面（視覚的明瞭度、視覚的テキストの依存関係）とテキスト的側面（テキストの明瞭度、概念的な難易度、推論の複雑さ）を評価します。
    *   **DRLC:** 動的推論長コントローラ（DRLC）は、QDAMから正規化されたスコアに基づいて推論チェーンの長さを調整します。複雑なクエリは長い推論チェーンを許可され、単純なクエリは短い推論チェーンを強制されます。
    *   **自己蒸留:** モデルは、まずDRLCによって決定された推論長で推論指向のデータを生成します。次に、GPT-4oが生成された回答の正しさを評価します。正しければ推論チェーンが保持され、そうでなければ修正されます。

    ```python
    def generate_cot(model, query, qdam, gpt4o):
        # QDAMを使用してクエリの難易度を評価
        Sv, St, Si = qdam.evaluate(query)
        # DRLCを使用して繰り返しペナルティを決定
        penalty = drlc.calculate_penalty(Sv, St, Si)
        # モデルを使用して、適応長のChain-of-Thoughtを生成
        cot = model.generate(query, repetition_penalty=penalty)
        # GPT-4oを使用して、回答の正しさを評価
        correct = gpt4o.evaluate(query, cot)
        return cot, correct
    ```

# HiFlow: Training-free High-Resolution Image Generation with Flow-Aligned Guidance

[View Paper](http://arxiv.org/abs/2504.06232v1)

## 1. 既存研究では何ができなかったのか

既存のText-to-Image (T2I) モデルは、テキストプロンプトから柔軟にコンテンツを生成できる点で目覚ましい進歩を遂げましたが、高解像度画像の合成においては以下の課題が残されていました。

*   **品質劣化と構造の崩壊:** 既存のT2Iモデルは、通常、解像度が制限されており（例えば、512x512）、より高い解像度の画像を生成しようとすると、品質が低下し、構造が崩壊する問題がありました。
*   **高コストなFine-tuning:** 高解像度画像を生成するために、T2Iモデルを高解像度のサンプルでfine-tuningする方法が提案されていますが、高解像度画像の収集やモデル固有のfine-tuningに大きなコストがかかります。
*   **アーキテクチャ依存性:** 既存のtraining-freeな手法は、モデル内部の特徴を操作するものが多く、U-Netアーキテクチャに特化した手法をDiTベースのモデルに適用するなど、アーキテクチャ間の転移性が制限されていました。
*   **不十分な詳細表現:** 低解像度画像の情報を構造ガイダンスとして利用する方法もありますが、低解像度のサンプリング終点のみを利用し、サンプリング軌跡の潜在能力が十分に活用されておらず、ディテールが不足していました。
*   **過度な制約:** Projected Flowを導入して高解像度生成をガイドする方法もありますが、アップサンプリングされた低解像度画像を理想的なprojected flowの終点として扱い、高解像度生成に過度な制約を課し、ディテールの生成を著しく制限していました。

## 2. どのようなアプローチでそれを解決しようとしたか

HiFlowは、これらの課題を解決するために、以下の3つの主要なアプローチを採用しました。

1.  **仮想参照フローの確立:** 高解像度空間内に仮想的な参照フローを確立し、低解像度フロー情報の特性を効果的に捉えることで、高解像度生成のためのガイダンスを提供します。この参照フローは、低解像度サンプリングフローの段階的な推定クリーンサンプルに基づいて構築されます。
2.  **フローアラインメントによるガイダンス:** 高解像度合成において、以下の3つの側面から参照フローによるガイダンスを行います。
    *   **初期化アラインメント (Initialization Alignment):** 低周波成分の一貫性を維持します。
    *   **方向アラインメント (Direction Alignment):** 構造的特徴の保存を促進します。
    *   **加速アラインメント (Acceleration Alignment):** 詳細な忠実度を維持します。
3.  **カスケード生成パラダイム:** まず、低解像度画像を生成し、そのサンプリング軌跡を高解像度空間にマッピングして参照フローを取得します。次に、この参照フローを使用してフローガイドされた高解像度生成を行います。

## 3. 結果、何が達成できたのか

HiFlowを用いることで、以下の成果を達成しました。

*   **高解像度画像品質の向上:** フローアラインメントガイダンスを活用することにより、T2Iモデルの高解像度画像合成の品質を大幅に向上させることができました。
*   **モデルアーキテクチャへの非依存性:** HiFlowは、内部モデルの特性に依存しないため、U-NetやDiTアーキテクチャなど、様々なモデルアーキテクチャに適用できます。
*   **最先端技術を凌駕する性能:** 広範な実験により、HiFlowが現在の最先端技術を凌駕する高解像度画像品質を達成することが検証されました。
*   **トレーニングフリー:** HiFlowはトレーニングフリーであるため、追加の学習データや計算資源を必要とせずに、既存のpretrainedモデルの潜在能力を引き出すことができます。
*   **多様な応用:** LoRA, ControlNet, 量子化といった技術と組み合わせることで、パーソナライズされた高解像度画像生成や計算コストの削減を可能にしました。

## 4. Limitationや問題点は何か

HiFlowには、以下の制限事項と問題点があります。

*   **参照フロー品質への依存:** HiFlowはトレーニングフリーであるため、生成能力は参照フローの品質に大きく依存します。参照フローに構造的な不規則性があると、最終的な生成物の品質が損なわれる可能性があります。
*   **モデルの改善による性能向上への期待:** モデルに依存しない性質を持つため、より高度なモデルと組み合わせることで改善が見込まれますが、そのためにはfine-tuningや調整が必要となる場合があります。
*   **計算コスト:** 方向アラインメントと加速アラインメントのためにFFT等の処理を行うため、計算コストが増加する可能性があります。
*   **パラメータ調整の必要性:** 初期化アラインメントのためのノイズ追加比率τや、方向・加速アラインメントのためのガイダンスの重みαt, βtなどのハイパーパラメータを適切に調整する必要があります。

## 5. 技術的な詳細について

HiFlowの技術的な詳細を以下に示します。

1.  **参照フローの構築:**
    *   低解像度画像を生成する際の各ステップで推定されるクリーンサンプル (`X_0←t_i`と表記) を利用します。
    *   これらのクリーンサンプルをアップサンプリング関数 `phi` を用いて高解像度空間にマッピングします (`phi(X_0←t_i)`)。
    *   高解像度空間におけるノイズ画像を仮想的なノイズ画像 (`X_t^vrt`) として定義します。
    *   これにより、参照フローにおけるノイズ画像とクリーンサンプルのペアを `(X_t^vrt, phi(X_0←t_i))` と定義します。

    ```python
    def construct_reference_flow(low_res_trajectory, phi):
      """
      高解像度空間における仮想参照フローを構築する

      Args:
        low_res_trajectory: 低解像度画像のサンプリング軌跡 (各ステップのクリーンサンプルを含む)
        phi: アップサンプリング関数

      Returns:
        reference_flow: 高解像度空間における仮想参照フロー (ノイズ画像とクリーンサンプルのペアのリスト)
      """
      reference_flow = []
      for noisy_sample, clean_sample in low_res_trajectory: #各ステップのノイズ画像とクリーンサンプル
        high_res_clean_sample = phi(clean_sample) #高解像度空間にアップサンプリング
        virtual_noisy_sample = generate_virtual_noisy_sample() #仮想的な高解像度ノイズ画像を生成
        reference_flow.append((virtual_noisy_sample, high_res_clean_sample))
      return reference_flow
    ```

2.  **初期化アラインメント:**
    *   高解像度生成の初期ノイズ (`X_1^high`) と参照フローのクリーンサンプル (`X_0←τ^ref`) を用いて、初期化を行います。
    *   ハイパーパラメータ `τ` は、ノイズの追加比率を調整します。

    ```python
    def initialize_high_resolution(high_res_noise, reference_flow_clean_sample, tau):
      """
      高解像度生成の初期化

      Args:
        high_res_noise: 高解像度ノイズ
        reference_flow_clean_sample: 参照フローのクリーンサンプル (t=tau)
        tau: ノイズ追加比率

      Returns:
        initialized_noisy_sample: 初期化されたノイズサンプル
      """
      initialized_noisy_sample = tau * high_res_noise + (1 - tau) * reference_flow_clean_sample
      return initialized_noisy_sample
    ```

3.  **方向アラインメント:**
    *   高解像度予測クリーンサンプル (`X_0←t^high`) と参照フローのクリーンサンプル (`X_0←t^ref`) の低周波成分が一致するように、FFTとローパスフィルタ (`L`) を用いて調整します。
    *   `alpha_t` は、方向ガイダンスの重みを制御します。

    ```python
    def direction_alignment(high_res_clean_sample, reference_flow_clean_sample, alpha_t, L):
      """
      方向アラインメント

      Args:
        high_res_clean_sample: 高解像度予測クリーンサンプル
        reference_flow_clean_sample: 参照フローのクリーンサンプル
        alpha_t: 方向ガイダンスの重み
        L: ローパスフィルタ

      Returns:
        aligned_clean_sample: 方向アラインメントされたクリーンサンプル
      """
      F = fft2d  # 2次元高速フーリエ変換
      iF = ifft2d # 2次元逆高速フーリエ変換
      term1 = iF(F(reference_flow_clean_sample) * L)
      term2 = iF(F(high_res_clean_sample) * L)
      aligned_clean_sample = high_res_clean_sample + alpha_t * (term1 - term2)
      return aligned_clean_sample
    ```

4.  **加速アラインメント:**
    *   高解像度生成と参照フローの加速を計算し、その差分を用いて高解像度フローを調整します。
    *   `beta_t` は、加速ガイダンスの重みを制御します。

    ```python
    def acceleration_alignment(high_res_flow_t_minus_1, high_res_flow_t,
                               reference_flow_t_minus_1, reference_flow_t, beta_t):
      """
      加速アラインメント

      Args:
        high_res_flow_t_minus_1: 高解像度フロー (t-1)
        high_res_flow_t: 高解像度フロー (t)
        reference_flow_t_minus_1: 参照フロー (t-1)
        reference_flow_t: 参照フロー (t)
        beta_t: 加速ガイダンスの重み

      Returns:
        aligned_flow_t_minus_1: 加速アラインメントされたフロー (t-1)
      """
      aligned_flow_t_minus_1 = high_res_flow_t_minus_1 + beta_t * (
          reference_flow_t_minus_1 - reference_flow_t - high_res_flow_t_minus_1 + high_res_flow_t
      )
      return aligned_flow_t_minus_1
    ```

# OmniSVG: A Unified Scalable Vector Graphics Generation Model

[View Paper](http://arxiv.org/abs/2504.06263v1)

## 1. 既存研究では何ができなかったのか

既存のSVG生成手法は、主に以下の点で課題を抱えていました。

*   **計算コストの高さ:** 最適化ベースの手法は、複雑なSVGを生成する際に計算コストが膨大になり、実用性に欠けていました。また、冗長なアンカーポイントを持つ非構造化されたアウトプットを生成してしまうという問題点もありました。
*   **表現力の限界:** 自己回帰的な手法は、テキストや画像から直接SVGを生成できますが、コンテキストウィンドウの制約や学習データの不足により、単純なアイコンしか生成できませんでした。複雑な構造や豊かな色彩を持つSVGの生成は困難でした。既存のデータセットも、単純なパスベースのSVGやモノクロアイコンに偏っていました。
*   **マルチモーダル対応の不足:** テキストと画像を組み合わせた指示に基づいてSVGを生成する能力が十分ではありませんでした。既存研究では、テキストと画像の理解が分離しており、テキストによる記述と生成されるSVGの間の効果的なアラインメントが不足していました。

## 2. どのようなアプローチでそれを解決しようとしたか

OmniSVGは、上記の課題を解決するために、以下の主要なアプローチを採用しました。

*   **Vision-Language Model (VLM) の活用:** 事前学習済みのVLM (Qwen2.5-VL) を活用することで、テキストと画像の情報を統合的に処理し、多様な生成モダリティ（Text-to-SVG, Image-to-SVG, Character-Reference SVG）を実現しました。
*   **SVGのトークン化:** SVGのコマンドと座標を離散的なトークンにパラメータ化することで、構造的なロジックと低レベルのジオメトリを分離しました。これにより、効率的な学習が可能になり、「座標の幻覚」問題も軽減され、複雑なSVG構造の表現力を維持しました。
    *   例えば、`M 10 20 L 30 40 C 50 60 70 80 90 100` というSVGコマンド列を、`[M_token, 10_token, 20_token, L_token, 30_token, 40_token, C_token, 50_token, 60_token, 70_token, 80_token, 90_token, 100_token]` のようなトークン列に変換します。座標も数値ごとに分割するのではなく、`<x, y>` のペアを一つのトークンとして扱います。
*   **大規模データセットの構築:** 200万件のアノテーション付きSVGアセットからなる大規模なマルチモーダルデータセットMMSVG-2Mを構築しました。アイコン、イラスト、アニメデザインなど、多様なSVGデータを含み、条件付きSVG生成タスクのための標準化された評価プロトコルを提供します。
*   **アトミックコマンドによる簡略化:**  SVGの複雑なXML文法を、Move To (M), Line To (L), Cubic Bézier (C), Elliptical Arc (A), ClosePath (Z) という5つの基本的なコマンドに簡略化しました。Fill属性についても数値化してトークンとして扱えるようにしました。これにより、曖昧さを排除し、統一的でシンプルなデータ構造を実現しました。

## 3. 結果、何が達成できたのか

OmniSVGは、以下の点で優れた性能を発揮しました。

*   **高品質・複雑なSVG生成:** 単純なアイコンから複雑なアニメキャラクターまで、多様なSVGコンテンツを高精度に生成することに成功しました。
*   **マルチモーダルな生成能力:** テキスト、画像、キャラクター参照など、複数のモダリティからのSVG生成を統一的なフレームワークで実現しました。
*   **既存手法を凌駕する性能:** 定量的・定性的な評価において、既存のSVG生成手法を大幅に上回る性能を示しました。
*   **編集可能性の向上:** 構造的なロジックとジオメトリの分離により、生成されたSVGの編集が容易になりました。
*   **多様なデータセットへの対応:**  MMSVG-2Mデータセットを学習することで、多様なスタイルと複雑さを持つSVGを生成できるようになりました。

## 4. Limitationや問題点は何か

OmniSVGには、以下のLimitationと問題点が存在します。

*   **自然画像の苦手性:**  OmniSVGはベクタースタイルの画像を生成することに成功していますが、自然画像への対応は不十分です。
*   **生成時間の長さ:** 複雑なサンプルに対して数万のトークンを生成する必要があるため、生成に時間がかかることがあります。
*   **マルチモーダルデータセットの偏り:** MMSVG-2Mデータセットは、アイコン、イラスト、アニメキャラクターに偏っており、他の種類のSVGデータ（例えば、技術図面や地図）の生成には適していません。
*   **評価指標の限界:**  Character-Reference SVGタスクにおいて、GPT-4oによる評価は主観的であり、客観的な評価指標が求められます。
*   **データセットの著作権:**  MMSVG-2Mデータセットはインターネットから収集されたデータを含んでおり、著作権の問題が潜在的に存在します。

**個人的に考える問題点:**

*   **パラメータ数の増大:** VLMを活用しているため、モデルサイズが大きくなり、学習・推論に必要な計算リソースが増大します。
*   **SVG特有の知識の欠如:** VLMは汎用的な知識を持っていますが、SVG特有の知識（例えば、パスの最適化やスタイルの適用）は十分に学習できていない可能性があります。
*   **生成されるSVGの構造の複雑さ:** 生成されるSVGの構造が複雑になりがちで、手動で編集することが難しい場合があります。

## 5. 技術的な詳細について

OmniSVGの技術的な詳細は以下の通りです。

1.  **アーキテクチャ:**
    *   ベースモデル: 事前学習済みのVision-Language Model (VLM) であるQwen2.5-VLを使用します。
    *   SVGトークナイザー: SVGのコマンドと座標を離散的なトークンに変換するカスタムトークナイザーを使用します。
2.  **SVGのパラメータ化:**
    *   SVGのコマンド (M, L, C, A, Z, F) と座標をトークン化します。
    *   座標 `<x, y>` を一つのトークンにマッピングすることで、シーケンス長を短縮します。`token = x * w + y` (wはハイパーパラメータ)
    *   Fill属性も数値化してトークンとして扱います。
    *   SVGシーケンスの開始と終了を示す特別なトークン (`<SVG_START>`, `<SVG_END>`) を追加します。
3.  **学習:**
    *   テキストと画像を入力として受け取り、SVGトークン列を自己回帰的に生成するように学習します。
    *   損失関数: 次のトークン予測損失 (next-token prediction loss) を使用します。

    ```python
    def next_token_prediction_loss(model, input_tokens, svg_tokens):
      """
      Calculate the next token prediction loss.
      Args:
        model: The language model.
        input_tokens: The input tokens (text and image).
        svg_tokens: The SVG tokens.
      Returns:
        The loss value.
      """
      # Concatenate input tokens and SVG tokens
      all_tokens = concatenate(input_tokens, svg_tokens[:-1]) # Exclude the last token for prediction

      # Get model predictions
      predictions = model(all_tokens)

      # Calculate loss based on the actual next tokens (shifted SVG tokens)
      loss = cross_entropy(predictions, svg_tokens[1:]) # Start from the second token

      return loss
    ```
4.  **推論:**
    *   トップKサンプリングとトップPサンプリングを組み合わせて、多様なSVGを生成します。

# Tuning-Free Image Editing with Fidelity and Editability via Unified Latent Diffusion Model

[View Paper](http://arxiv.org/abs/2504.05594v1)

## 1. 既存研究では何ができなかったのか

テキストによる画像編集(TIE)において、既存研究は主に以下の点で課題がありました。

*   **忠実度と編集性のバランス**: 既存の手法は、構造の維持のためにattention injection、編集性のために事前学習済みのtext-to-image (T2I)モデルのテキストアラインメント能力に依存していましたが、これら2つの目的を適切にバランスさせるための明示的かつ統一的なメカニズムが欠けていました。バランスが崩れると、過剰な編集(over-editing)や不十分な編集(under-editing)の問題が発生していました。
*   **ハイパーパラメータ調整**: 既存のdual-branch editing paradigmは、主にattention injectionのタイムステップなどのハイパーパラメータを調整することでバランスを取っていましたが、様々な編集タイプに合わせた適応的な調整が困難でした。
*   **統一的なフレームワークの欠如**: 忠実度と編集性を明示的にモデル化し、統一的なフレームワーク内でバランスを取る方法が十分に研究されていませんでした。

## 2. どのようなアプローチでそれを解決しようとしたか

本研究では、UnifyEditというチューニングフリーの手法を提案し、以下の主要なアプローチで既存研究の課題を解決しようとしました。

*   **Diffusion latent optimization**: 拡散潜在空間を最適化することで、忠実度と編集性のバランスの取れた統合を可能にする統一フレームワークを構築しました。
*   **Attention-based constraint**: 構造的な忠実度を保つためのself-attention (SA) preservation constraintと、編集性を向上させるためにテキストアラインメントを促進するcross-attention (CA) alignment constraintという、2つのattentionベースの制約を開発しました。
*   **Adaptive time-step scheduler**: 2つの制約のgradient conflictを解決するために、各制約の影響を動的に調整するadaptive time-step schedulerを導入しました。これにより、拡散潜在空間を最適なバランスへと導きました。

## 3. 結果、何が達成できたのか

提案手法UnifyEditにより、以下の成果が達成されました。

*   **忠実度と編集性のロバストなバランス**: 様々な編集タスクにおいて、構造の維持とテキストアラインメントのバランスを達成し、既存の最先端手法を凌駕しました。
*   **チューニングフリー編集**: 事前学習済みのT2Iモデルを、再学習やファインチューニングなしで適応させることが可能になりました。
*   **統一フレームワーク**: 忠実度と編集性を明示的にモデル化し、適応的な調整を可能にする統一的なdiffusion latent optimizationフレームワークを確立しました。
*   **Gradient可視化**: 制約のgradientを可視化することで、過剰編集や不十分編集の原因を特定し、ユーザーが忠実度と編集性のトレードオフを調整できるようになりました。

## 4. Limitationや問題点は何か

*   **非剛体変換への対応**: 提案されたSA preservation constraintは、レイアウトとセマンティック情報を捉えるため、ターゲットオブジェクトの剛性を制約する可能性があります。そのため、座っている犬をジャンプしている犬に変えるような非剛体変換には課題が残ります。
*   **複雑な形状変化**: 物体置換など、大幅な形状変化を伴う編集では、ソース画像の構造情報を維持しつつ、テキストプロンプトに沿った編集結果を得ることが難しい場合があります。
*   **ハイパーパラメータ調整**: adaptive time-step schedulerには、β1, β2, k1, k2といったハイパーパラメータが存在し、タスクやユーザーの好みに応じて調整する必要があります。

*   **汎用性**: Stable Diffusion v1.4モデルをベースに評価されているため、他のdiffusion modelや、より複雑なシーン、抽象的な編集指示に対する汎用性は不明です。

## 5. 技術的な詳細について

UnifyEditは、事前学習済みのT2I diffusion modelをベースに、diffusion latent optimizationを利用して、忠実度と編集性のバランスを取る手法です。

1.  **Dual-Branch Paradigm**: 一般的なdual-branch paradigmを採用し、source promptとtarget promptに基づいて、それぞれsource branchとtarget branchを生成します。

2.  **Attention-Based Constraint**: 忠実度と編集性のために、それぞれSA preservation constraintとCA alignment constraintを定義します。

    *   **SA Preservation Constraint (L_SAP)**: source branchとtarget branchのSA mapの差異を最小化することで、構造的な忠実度を維持します。

        ```python
        def calculate_sa_preservation_loss(sa_source, sa_target):
            loss = sum((sa_source - sa_target)**2)
            return loss
        ```

    *   **CA Alignment Constraint (L_CAA)**: target promptに対応する領域のCA値を最大化することで、テキストとのアラインメントを促進し、編集性を向上させます。

        ```python
        def calculate_ca_alignment_loss(ca_target, mask):
            # maskの内側と外側のCA値の比率を計算
            inside_mask = sum(ca_target[mask > 0]) / len(ca_target[mask > 0]) if len(ca_target[mask > 0]) > 0 else 0
            outside_mask = sum(ca_target[mask == 0]) / len(ca_target[mask == 0]) if len(ca_target[mask == 0]) > 0 else 0

            ratio = inside_mask / outside_mask if outside_mask > 0 else 0 # outside mask = 0で計算が破綻するのを防ぐ
            loss = -sum(ratio**0.5)**2 # ratioの平方根の合計を最大化（lossなので-をつける）
            return loss
        ```

3.  **Adaptive Time-Step Scheduler**: SA preservation constraintとCA alignment constraintを同時に適用すると、勾配が競合し、どちらかの制約が優位になることで過剰編集や不十分編集が発生する可能性があります。これを解決するために、denoisingのタイムステップに応じて各制約の重みを動的に調整するadaptive time-step schedulerを導入します。

    ```python
    def adaptive_time_step_scheduler(timestep, T, beta1, beta2, k1, k2):
        lambda1 = beta1 * (1 - math.exp(-k1 * (T - timestep))) # SA preservation constraintの重み
        lambda2 = beta2 * math.exp(-k2 * (T - timestep)) # CA alignment constraintの重み
        return lambda1, lambda2
    ```

4.  **Latent Optimization**: 拡散過程において、latent variableをiterativelyに更新し、定義された制約を最小化することで、望ましい編集結果を得ます。

    ```python
    def unify_edit(z_t, prompt, prompt_star, T, beta1, beta2, k1, k2, max_iter):
        # 初期化
        z_t_star = z_t # z_tの初期値をz_t_starとする

        for i in range(max_iter):
            # SA mapとCA mapを計算
            _, sa_t, _ = stable_diffusion(z_t, prompt, t)
            _, sa_t_star, ca_t_star = stable_diffusion(z_t_star, prompt_star, t)

            # SA Preservation LossとCA Alignment Lossを計算
            L_SAP = calculate_sa_preservation_loss(sa_t, sa_t_star)
            L_CAA = calculate_ca_alignment_loss(ca_t_star, mask)

            # Adaptive Time-Step Schedulerで重みを計算
            lambda1_star, lambda2_star = adaptive_time_step_scheduler(t, T, beta1, beta2, k1, k2)

            # 勾配を計算
            grad_SAP = calculate_gradient(L_SAP, z_t_star) # calculate_gradientはL_SAPに関するz_t_starの勾配を計算する関数
            grad_CAA = calculate_gradient(L_CAA, z_t_star) # calculate_gradientはL_CAAに関するz_t_starの勾配を計算する関数

            # 勾配を正規化
            grad_SAP_norm = grad_SAP / norm(grad_SAP) # normはL2ノルムを計算する関数
            grad_CAA_norm = grad_CAA / norm(grad_CAA) # normはL2ノルムを計算する関数

            # 重み付けされた勾配を計算
            G_blc = lambda1_star * grad_SAP_norm + lambda2_star * grad_CAA_norm

            # latent variableを更新
            z_t_star = z_t_star - mask * G_blc

            # DDIMで次のタイムステップを計算
            z_t_minus_1_star = ddim_step(z_t_star, prompt_star, t) # ddim_stepはDDIM samplingを行う関数

        return z_t_minus_1_star # 最終的なz_t_minus_1_starを返す
    ```

# Hogwild! Inference: Parallel LLM Generation via Concurrent Attention

## 1. 既存研究では何ができなかったのか

既存の並列LLM推論フレームワークは、主に以下の点で制約がありました。

*   **固定された協調戦略:** 多くの手法（Self-Consistency、Skeleton-of-Thought (SoT) など）は、事前に定義された並列化戦略（投票、タスク分割など）に依存しており、問題の種類によっては非効率になる場合がありました。例えば、SoTのような手法では、初期計画が誤っている場合や、サブタスクの難易度が予想と異なる場合に、柔軟に対応できませんでした。

*   **計算オーバーヘッド:** 役割ベースの議論を行うフレームワークでは、一部のエージェントが問題を逐次的に解決し、互いの進捗を再エンコードする必要があり、計算コストが増加していました。

*   **普遍的な解決策の欠如:** 特定の並列化戦略がすべての問題に有効であるとは限らず、問題の性質によっては性能が低下する可能性がありました。

## 2. どのようなアプローチでそれを解決しようとしたか

本研究では、事前定義された協調フレームワークに頼らず、複数のLLMインスタンスが動的に相互作用し、問題に対して最適な協調戦略を自ら考案できるような新しい並列推論プロトコル「Hogwild! Inference」を提案しました。

*   **共有Key-Valueキャッシュ:** 複数のLLMインスタンス（ワーカー）が、同時に更新される共有Key-Valueキャッシュを介して情報を共有し、互いの生成したトークンに「瞬時」にアクセスできるようにしました。

*   **Rotary Position Embeddings (RoPE)の活用:** RoPEを利用することで、トークンの位置情報を調整し、再計算を回避しながら並列ハードウェアの利用率を向上させました。

*   **プロンプトによる協調誘導:** LLMワーカーに対して、共有キャッシュのレイアウトに関するルールを説明し、協調の例を示すプロンプトを与えることで、ワーカーが自律的に協調戦略を策定するように促しました。具体的には、冗長な作業をしていないか定期的に確認させるプロンプトを挿入しました。

## 3. 結果、何が達成できたのか

Hogwild! Inferenceにより、以下の成果が得られました。

*   **動的な協調:** 複数のLLMインスタンスが、互いの進捗を考慮しながら、自律的に協調戦略を策定し、問題解決に取り組む様子が観察されました。例えば、初期計画の失敗時に計画を修正したり、互いの誤りを指摘したり、重要な観察結果を共有したりするなどの行動が見られました。

*   **効率的な並列推論:** 共有Key-ValueキャッシュとRoPEの活用により、計算コストを抑えながら、並列ハードウェアの利用率を向上させ、推論の高速化を実現しました。

*   **既存モデルの活用:** 追加のファインチューニングなしに、既存の推論能力の高いLLM（QwQなど）が、共有キャッシュを用いた並列推論を効果的に実行できることが示されました。

## 4. Limitationや問題点は何か

*   **プロンプトへの依存:** 協調的な推論はプロンプトに依存しており、プロンプトの設計が性能に大きく影響する可能性があります。最適なプロンプト戦略はまだ確立されていません。

*   **タスクへの依存:** Hogwild! Inferenceの効果はタスクの種類によって異なり、厳密な逐次ロジックを必要とするタスクでは並列化によるメリットが少ない可能性があります。

*   **非決定性:** 並列推論は、スレッド間のタイミングなどのわずかな相互作用によって最終的な出力が異なる可能性があり、非決定性を導入します。

*   **冗長性の排除の不確実性:** LLMは冗長な作業を認識できるものの、常に最適な行動を取るとは限りません。

*   **評価の初期段階:** 実験は初期段階であり、様々なタスクやモデルに対する汎用性や性能をより詳細に評価する必要があります。

## 5. 技術的な詳細について

Hogwild! Inferenceの技術的な詳細は以下の通りです。

*   **共有Key-Valueキャッシュ:** 複数のLLMインスタンスが、共通のKey-Valueキャッシュを共有します。キャッシュは複数のブロックに分割され、各ワーカーはこれらのブロックを再利用できます。

*   **Rotary Position Embeddings (RoPE):** RoPEの並列シフトに対する不変性を利用して、KVブロックを推論中に正しい位置に回転させます。これにより、トークンの再エンコードを回避し、計算コストを削減します。

*   **キャッシュレイアウト:** 実験では、以下の3つのキャッシュレイアウトを比較しました。
    *   **contiguous:** 各ワーカーが自身のトークンを連続した領域に書き込み、他のワーカーのトークンを過去のキーと値として参照します。
    *   **interleaved:** 各ワーカーが他のワーカーのトークンを異なる順序で配置し、共通のプロンプトキャッシュの後に、他のワーカーのキャッシュ、自身のキャッシュの順で参照します。
    *   **hybrid:** 各ワーカーが共有履歴にステップを蓄積し、他のワーカーの現在の進捗を即座に参照できるようにします。

*   **並列処理:** 全てのワーカーに対して、順伝播をバッチ処理のように並列に実行します。

```python
# Hogwild! Inferenceの疑似コード

def hogwild_inference(model, prompt, num_workers, cache_layout):
  """
  並列LLM推論を実行する

  Args:
    model: LLMモデル
    prompt: 入力プロンプト
    num_workers: ワーカー数
    cache_layout: キャッシュレイアウト (contiguous, interleaved, hybrid)

  Returns:
    生成されたテキスト
  """

  shared_kv_cache = initialize_shared_kv_cache(prompt) # 共有KVキャッシュの初期化
  workers = [create_worker(model, shared_kv_cache) for _ in range(num_workers)] # ワーカーの作成

  generated_tokens = []
  while not termination_condition(): # 終了条件を満たすまで
    # 各ワーカーで並列にトークンを生成
    new_tokens = parallel_map(workers, lambda worker: worker.generate_token())

    # 新しいトークンを共有KVキャッシュに追加
    update_shared_kv_cache(shared_kv_cache, new_tokens, cache_layout)

    # 生成されたトークンを記録
    generated_tokens.extend(new_tokens)

    # プロンプトによる協調誘導 (例：冗長性チェック)
    for worker in workers:
      if should_check_redundancy(worker):
        prompt_for_redundancy_check(worker, shared_kv_cache)

  return generated_tokens

def create_worker(model, shared_kv_cache):
  """ワーカーを作成する"""
  class Worker:
    def __init__(self, model, shared_kv_cache):
      self.model = model
      self.shared_kv_cache = shared_kv_cache
      self.local_cache = None

    def generate_token(self):
      """トークンを生成する"""
      # 共有KVキャッシュに基づいて次のトークンを予測
      token = self.model.predict_next_token(self.shared_kv_cache, self.local_cache)
      return token
  return Worker(model, shared_kv_cache)

def update_shared_kv_cache(shared_kv_cache, new_tokens, cache_layout):
  """共有KVキャッシュを更新する"""
  # キャッシュレイアウトに基づいてKVキャッシュを更新
  if cache_layout == "contiguous":
    update_contiguous_cache(shared_kv_cache, new_tokens)
  elif cache_layout == "interleaved":
    update_interleaved_cache(shared_kv_cache, new_tokens)
  elif cache_layout == "hybrid":
    update_hybrid_cache(shared_kv_cache, new_tokens)

def prompt_for_redundancy_check(worker, shared_kv_cache):
  """冗長性チェックのためのプロンプトを生成する"""
  # 共有KVキャッシュを基に、冗長性があるか確認するプロンプトを生成
  prompt = create_redundancy_check_prompt(shared_kv_cache)
  # ワーカーにプロンプトを与え、応答を基に作業を調整
  worker.adjust_strategy(prompt)
```
